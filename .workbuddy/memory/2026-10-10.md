## 「能否作为静态网站部署」的核查结论

产物 `霞光预报.html`（345,059 B）是**单文件、零构建、零服务端**：
所有 JS/CSS/城市表都内联，唯一 `<script src>` 是 `https://map.qq.com/api/gljs`。
→ **可以作为静态站点部署。**

### 唯一硬阻塞：地图代理占位符（3 处）
```js
window._TMapSecurityConfig = {
  serviceHost: 'http://127.0.0.1:__WB_HTTP_PORT__/_TMapService/_wbt/__WB_TMAP_SECRET__' };
```
这是**设计如此**，不是疏漏 —— 腾讯地图 secret 不能进前端，运行环境起本地代理 `_TMapService`
把它藏在服务端。自己部署时两重不成立：① 占位符没人替换；② `127.0.0.1:port` 在公网不成立。
- 出路 A：不管它 → 地图降级，**其余 7 个模块全可用**（有兜底文案；但那句
  "请在本应用的预览/分享页里打开"在独立部署下显得怪，应改）
- 出路 B：自建反代转发到 `map.qq.com`，secret 留在服务端，`serviceHost` 指向自己域名

### 三处注意
1. **HTTPS 混合内容**：站点 HTTPS + `serviceHost` 是 http → 浏览器直接 block。方案 B 必须 HTTPS。
2. **运行时外部依赖**（均浏览器直连，无需自建转发）：
   `api.open-meteo.com` / `air-quality-api.open-meteo.com`（气象，CORS ✅）、
   `geo.datav.aliyun.com`（省界 GeoJSON，无 key，挂了只影响描边）、`map.qq.com`（底图）。
3. **额度会被放大**：免费层按**出口 IP** 计。每访客首屏 65、点一次地图 +171
   → 约 **150 次访问/天**打满；共享 NAT 出口还会与陌生人共用配额。
   公开站点应走付费 Standard（$29/月 1M）或自建 Open-Meteo（AGPLv3）。
   另：免费层**仅限非商业**。

### 待验证
平台（预览/分享页）到底会不会自动替换那两个占位符 —— 待实际发布一次即可确认。

## 更正：额度归属（推翻上文第 3 条的部分推断）

上文"约 150 次访问/天打满"**是错的** —— 默认了 10,000/天 是站点共享配额。
**免费层不发 API key**（付费层才是 `customer-api.open-meteo.com` + `&apikey=`），
请求里没有任何标识应用/账号的参数 ⇒ 服务端**只能按请求来源 IP 归属**。
本项目纯前端、访客浏览器直连（`_p4.js:4` `API_FORECAST = "https://api.open-meteo.com/v1/forecast"`），
请求**不经过任何服务器** ⇒ 计入的是**访客自己的 IP**，10,000/天 是**每位访客各自**的额度。
**站点本身不消耗任何配额。**

官方原文（已抓 open-meteo.com/en/terms + /en/pricing）：只写「Less than 10'000 API calls per day…」，
未界定归属维度，但有「block applications **and IP addresses** that misuse our service」，
印证 IP 是实际管控单位；隐私章节也写明会收集 IP 以 prevent misuse。

真正该注意的两条（与部署方式无关，现状就已存在）：
1. 免费层**仅限非商业** —— 有订阅或展示广告的站点、集成进商业产品都算商业。
2. terms 保留封 IP 的权利 ⇒ **共享 NAT / 公司/学校出口下，同 IP 的陌生人共用这 10,000/天**。

## 「B 方案（服务端代转）能否直接挂 Cloudflare Pages」的核查结论

**技术上不需要自建服务器，但在 Cloudflare 上做 API 代理是反优化 —— 达不到 B 的目的。**

关键证据（**Open-Meteo 作者本人**，HN/whnex 转述原话）：
> The limits are 600 calls / min, 5.000 calls / hour and 10.000 calls / day.
> **Limits are applied on an IP basis. This is not ideal for shared hosting services
> like cloudflare workers**, but is the easiest and privacy-friendly way to limit access to fair-use.

Cloudflare 侧证据：Workers 出站请求**不能指定 IP**，全部走 Cloudflare 自己的（极小）地址池 ——
Cloudflare 员工 Walshy 在官方 Discord 答：「No, this is fully intended」，
且实测所有 Worker 的 `icanhazip.com` 返回同一个 IP（`2a06:98c0:3600::103` 一族）；
另有工程师答「Workers will use any IP from the IP pool, and you can't force it to use one」。
⇒ 代理 open-meteo 等于**与全球所有 Cloudflare Workers 用户共用**那一份 10,000/天，
几乎必然已被打满 → 冷启动/缓存未命中时直接 429。

**结论：B 方案要有意义，就必须拿到独占出口 IP ⇒ 自建 VPS，而不是 Workers。**
B 的真正价值也不在"换 IP"（换不成），而在**服务端缓存**（把 171 次/访问变成按 (城市,日期) 复用）。

Cloudflare 免费层的实际额度（已核实，供参考）：
- Workers / Pages Functions 共享池 **100,000 请求/天**（UTC+0 重置），静态资源请求**免费不限量**
  且**不计入**该池（靠自动生成的 `_routes.json` 排除）
- **10 ms CPU / 次调用**（等网络的时间不计入 CPU ⇒ 纯代理转发够用）
- **50 subrequests / 请求**（本项目每次只需 2–4 个 upstream HTTP 请求，余量极大）
- 日限额用尽时默认 **Fail open**：Functions 被旁路、静态资源照常服务（天然的降级）
- ToS 不是障碍：2023 年已删掉旧的 §2.8（HTML/non-HTML 构造），内容限制移到 CDN 专属条款，
  且明确 **Developer Platform 不受此限**，新版条款还写明 CDN 可用于 serving web APIs

**A 方案在配额上反而优于 B**（分散到每个访客），只是仍受"共享 NAT"与"非商业"两条约束。
若将来真要服务端化，正确顺序是：自建 VPS 独占 IP（或自托管 Open-Meteo，AGPLv3，可商用、无限调用）
→ 静态资源仍可放 Cloudflare Pages（免费、无限带宽）。

产出：`部署方案对比.md`（A / B / 自托管三条路的对比与建议）。

## 追加：地图模块在 A 方案下**不需要舍弃**（四条路）

已核实：腾讯位置服务**官方就提供**这套代理转发（文档 `glKeyDelegate`
「JavaScript API GL · Key 安全 / 代理服务转发」，原话：「明文 Key 仅限本地，
公网发布必须改用代理方案」）。产物 `tpl/template.html:576-580` 的写法与官方示例**逐字一致**。
代理只需实现**四条路由**（Nginx 原文，key 由服务端注入）：

| 路径 | 上游 | 加的参数 |
|---|---|---|
| `/_TMapService` | `https://pr.map.qq.com/pingd?appid=jsapi_v3` | `&key=` |
| `/_TMapService/checkKey` | `https://apikey.map.qq.com/mkey/index.php/mkey/check` | `&key=` |
| `/_TMapService/oversea` | `https://overseactrl.map.qq.com` | `&apikey=` |
| `/_TMapService/service` | `https://apis.map.qq.com/ws` | `&key=` |

**关键纠正（此前回答的盲点）**：地图代理与气象数据代转是**两件独立的事**。
上文"B 方案在 Cloudflare 上失效"**只针对 Open-Meteo**（按来源 IP 限流 + Workers 出口 IP 共享）；
**腾讯地图不按来源 IP 限流**，它认你自己的 key + 配额（QPS）。
⇒ **地图代理放 Cloudflare Pages Functions 完全可行，不需要 VPS**，
且 `serviceHost` 与站点**同源** ⇒ 没有 CORS、没有混合内容问题。

**产物对地图引擎的依赖很薄**（`_p6.js` 只用了四处）：
`new TMap.Map` / `TMap.LatLng` / `map.projectToContainer`（出现 4 次）/ `TMap.MultiPolygon`+`PolygonStyle`（省界）
+ 地图事件。**色面、可信度纱、数值直标、图钉、提示卡、图例全是自绘的**（`TMap.visualization.Heat` 刻意不用）
⇒ 无论选哪条路，自绘图层都不用重写。

四条路：**路 0** 明文 key + Referer 白名单（1 行，官方定性"仅限本地"）；
**路 1** 什么都不做先实测（**零成本，推荐先做**）；**路 2** 官方代理转发（~40 行 Pages Function，
key 存环境变量）；**路 3** 换 Leaflet/MapLibre（⚠️ 中国区域地图展示需测绘资质，**不建议**）。

**路 1 的实测要点**：`map.qq.com/api/gljs` 这个脚本**本来就不带 key**（官方示例即如此），
所以 `window.TMap` 大概率能正常出现；真正受影响的只是 `serviceHost` 那几条服务请求。
`_p6.js:403` 已把失败分成三类，实测后就知道落在哪一类。

**顺带记下（供 future 改动）**：`_p6.js:413` 用 `/__WB_/.test(host)` 判"是否仍是占位符"，
所以自定义 serviceHost 必须把 `__WB_HTTP_PORT__` 与 `__WB_TMAP_SECRET__` **两个都替换掉**，
否则会误报成占位符。

### 两处反事实（"修它值不值"的依据）

1. **放宽掩膜**：拿页面里真实位图做可分离定距膨胀（`KEEP_KM=300`），换掉 `g.land`
   重跑 `buildField` 读真实像素 alpha —— 三亚保留格 **4045 → 14093（×3.48）**、
   被裁点 **37 → 1**、榜前 8 不可见 **8 → 1**。探针跑完已复原掩膜。
2. **归零复选框 min-width**：**0 px / 0 行都不省** → 定性为**纯观感**（该结论直接改了它的优先级）。

### 三处把自己的测量写错了、当场纠正

- **"死区"指标**：原用 `label 宽 − input 宽`，那其实等于"文字宽 + 间隙"，四个汉字就 52 px
  ⇒ 看着像死区但不是。改成"被撑宽的像素 = input 宽 − 13（不依赖任何渲染假设）"。
- **行数分组**：原按 `rect.top` 精确值分组，同一行里 select(36px) 与 label(20px) 因
  `align-items:center` top 各不同 ⇒ 一行数成三行。改用**垂直区间重叠**分组。
- **反事实打偏**：段 D2 第一版跑在"8 城扫描的最后一站"（乌鲁木齐，只被裁 1 点）⇒ 无信息量。
  改成**对准被裁最严重的那个城市**（三亚）再测。

### 结论性判断（也写进了 MEMORY 硬约束 34/35）

- **不用 ETOPO1 判海**：实测 10 个已知点错 2 个，且错的都是最坏方向 ——
  0.5°＋双线性把陆地高程抹到海上，**上海外海 60 km 读 0 m**，而岸线外 0–60 km
  正是霞光最关键、精度又最差的那条带。→ 用位图膨胀（确定性、零新数据）。
- **不必升 `MAP_CACHE_PREFIX`**：查了 `mapCachePut`，落盘的是 `{ts,obj}` 逐点数据，
  几何是内存派生的 ⇒ 掩膜不进缓存。
- **不必改 `localgrid.js` / `zoomprobe.js` / `cdp.js`**：分别是"只测开关"、
  "手工色面不含掩膜"、"纱断言读的就是已掩膜 alpha（自动跟随）"。
- **图层号要重排才能插方位环**：3(直标)/4(图钉)/5(遮罩) 都占了 ⇒ 方位环取 3、
  其余顺延 4/5/6；`cdp.js` 的 `dimZ<rlZ` 仍成立。
