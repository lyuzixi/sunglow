### F3 · 最佳窗口日历（`_p5.js` 的 `renderTrendCal`）
把趋势的 `rows` 换一种读法：不按"逐日两列数字"，而按"**未来这些天哪天值得去**"。
- 每格：日期 + 星期 + 朝/晚两行（等级色块 + 质量分 + 概率），在**前三名**格子上描边；
  下方一行"最值得去：10-13 晚霞 81 分 · …"。
- 点格子 ⇒ 切到那天那个时段（优先保持当前时段，那天没数就用有数的那个）。
- **零取数的边界要写清**：零取数指**渲染这张日历**（只读已算好的 `t.rows`，所以切语言、
  切主题、随便重画都不花钱）；**点格子**是用户的显式意图，照常走一次单点取数。
  （踩过：`runForecast(scroll)` 的参数是"**是否滚动到结果卡**"，不是 cacheOnly ——
   我一开始照抄趋势表格的调用，还在注释里写"走缓存、不取数"，是错的，已改正。）

### F2 · 多观测点对比（`_p5.js` 的 spots 一整套）
收藏最多 5 个机位，一次取数横向排序（按质量分），回答"今天去哪儿拍"。
**额度纪律的三条落法**（这是本功能最关键的部分）：
1. 取数**只能**由「对比这些点」按钮触发 —— 打开页面只画列表，零请求；
2. 命中**单点缓存**的点**不进请求**（用的就是普通单点缓存的键族，所以"先单独查过某点"
   再对比，那一点零成本）。实测：3 个点里广州首屏查过 ⇒ 只取 2 个点的坐标（2×17=34）；
3. 默认**只比当前时段**，坐标数 17N 而不是 34N。
上限 5：界面上写明"本次将消耗约 N 个计费调用"。
- `spots` 存**独立键** `sunsetbot.spots.v1`（这是**数据**不是显示偏好），坏值一律丢弃
  （越界坐标/非数值/坏 JSON），名字走 `safeLabel`（与 URL 地名同一条纪律）。
- **三处失效**：位置 / 日期 / 时段任一变化 ⇒ `State.spotRows = null`（否则会显示
  上一个地点或上一天的数字 —— 这类"静默错位"是本项目的老对手）。

## F5 · 结果快照分享链接（2026-10-13 完成，commit aa2f43c）

### 做了什么
带 `snap=` 的链接 → **零取数**直接出结论卡。核心：只存"键 + 数"，不存"文案"。

- `_p2.js`：`b64uEnc` / `b64uDec`（base64url —— 中文地名过 `encodeURIComponent` 是
  9 字符/字，base64 的 `+/=` 又要被再转义一次，base64url 直接进查询串）。
- `_p5.js`：`baseQuery()` 抽出公共查询串（`syncUrl` 与快照链接共用）；`SNAP_VER/MAX/TYPES/DECKS`、
  `snapEncode` / `snapDecode` / `snapUrl` / `copySnap` / `legacyCopy` / `snapMsg` /
  `invalidateSnap` / `applySnap`；`readUrl` 解出 snap 后**由快照反填** lat/lon/date/period/name。
- `_p5b.js`：`SNAP_FACTORS`（12 项，`fmt` 与 `renderFactors` 的显示串等价）+ `SNAP_KEYS` 白名单；
  `renderSnap` / `snapGenTxt` / `snapAgeH`。
- `_p5b.js` 的 `renderFactors`：`add()` 改成 `(key, name, numVal, val, score, desc)`，
  顺手把 `[键, 原始数值, 得分]` 记进 `State.factorRows` —— **12 组 `trap()` 阈值仍然只有一份**。
- `tpl/`：`#snapUrl` 按钮 + `#snapOut` 兜底区 + `body.snapmode [data-snaphide]{display:none}`（③④⑤⑥ 收起）。
- `_p6.js`：`relang()` 里快照优先于完整结果重渲（切语言 ⇒ 快照卡跟着变）。

### 四条硬纪律（改这里之前先读 `_p5.js` 那段注释）
1. 只存键与数：云型 / 因素名存**内部键**，展示时才 `i18n()` ⇒ 同一条链接切英文就是英文。
2. 解码即校验：日期正则 / 时段白名单 / 云型下标白名单 / 数值 `parseFloat+isNum` / 字符串 `safeLabel`。
3. 解码**前**先量长度（`SNAP_MAX=2000`）⇒ 一条几 MB 的 snap= 不会白跑解码。
4. 日出日落时刻与方位角**不进链接**：由 (lat, lon, date, tz 分钟偏移) 用 `sunEvents` /
   `solarPosition` 现算 ⇒ 想改时刻就得连地点日期一起改。

### 关键设计决策
- **`State.booting` 闸门**：`initUI` 里那次 `setLocation()` 是"铺初值"不是用户改地点，
  否则首屏就会把刚从 URL 读进来的快照判死。
- **失效只收口在 `invalidateSnap()` 一处**（改地点 / 改日期 / 改时段 / 算成功 / 算失败）。
  它只清 State，地址栏靠随后那次 `syncUrl()` 自然去掉 snap= —— 不在 syncUrl 里再判一次
  "快照还匹配不匹配"。
- **快照模式不跑 `runForecast`**：首屏自动预报是本项目唯一一处被动取数，有快照还照跑
  等于把"不花对方额度"这个承诺作废。

### 探针 `_check/snapprobe.js`（24 条断言）
踩的两个坑，**都是判据写错**（不是功能错）：
1. 恶意地名 `<img src=1 onerror=…>` 经 `safeLabel` 后变成 "img src1 onerrorwindow.p"，
   **"onerror" 作为纯文本出现在 DOM 里**。我按"字符串是否出现"判 ⇒ 把安全误判成危险。
   正确判据：`onerror=`（带等号）不出现 + 没有任何带 on* 属性的元素 + 没有 img/script/iframe，
   **同时**断言 payload 的文本确实在 `.big` 里（证明走到了渲染路径，不是"整条被拒"的空绿）。
2. 「重新计算」那一步**命中了单点缓存**（前面已取过同一天）⇒ 请求数 0，我却断言 ≥1。
   与 F2 那次是同一个坑。改成"完整因素表拿回来了"（`facRows >= 10`）。
- 另配一条**判据自检**：不带 snap 的首屏必须产生请求，否则"快照页 0 请求"是空转绿灯。
- 实测：快照串 187 字符 / 整条 URL 343 字符 / 快照页与恶意载荷页均 0 次请求 /
  `__pwned` 始终 undefined / 注入元素 0 / on* 属性 0。
