1.1 功能面差异解读

  • 「多源」语义不同：Skyglow 的「四源」是四套气象资料（同族不同模式），回答「哪个模式的场更可信」；sunglow 的「三路」是算法（统计判据 ×2 + 光追），其中两路共用 GFS/ECMWI 场并经微扰产生分歧，回答「哪类算法更可信」。前者贵在数据多样性，后者贵在方法多样性。
  • 地图是两极分化最重的模块：Skyglow 有全国覆盖但制图语言朴素（自绘 Canvas、无底图瓦片）；sunglow 只有 500 km 局部但制图专业（腾讯底图、等值线、掩膜、图钉卡片、全屏）。这与两者的合规策略直接相关：sunglow 明示「境内展示地图需测绘资质，腾讯合规，换 OSM 等于把合规问题换进来」（README §2.2.1 合规段）；Skyglow 则完全规避第三方底图服务，仅用 DataV 省界作参考层（Skyglow/README 边界段）。
  • 时间纵深：Skyglow 借 ERA5 档案把日历拉到 1980 年起；sunglow 全部依赖 Forecast 端点，天然只有预报时域（且只用最近 17 天窗口）。对「复盘去年那次晚霞」类需求，只有 Skyglow 能回答。
  • 产品外壳：sunglow 把大量工程投在了「非预测」体验上（i18n、主题、分享、PWA、教程、对比、日历、校准），Skyglow 则几乎全部投在「预测本身」（数据源、标定、验证、直连）。

2.3 算法层判断

  • 采样几何：Skyglow 的 25 点环带天然覆盖「太阳方向整个上游扇区」，对「地平线有没有云挡光」这一主机制采样更充分（README 记录了裁剪实验：仅中心点最差偏差 42.3pp）；sunglow 的 17 点样带是沿方位的一维剖面，额外产出云盘边界距离 dNear/dFar，直接喂给火三角算持续时长——几何用途更深，但侧向（±方位）信息缺失。两者各有侧重，无绝对优劣。
  • 光谱模型：sunglow 的数值积分更「重」（曲率修正 + 漫射天光 + 洗白 + OKLab 彩度），概念上更完整；Skyglow 的解析大气质量更快且与切点高度闭式联系，适合服务端逐点批量（608 + 169 格点）。精度孰优无第三方基准，仓库内均未做交叉标定。
  • 合成哲学：sunglow 是「物理量 → 手工隶属函数 → 固定权重」，透明度高但不可自证；Skyglow 是「物理量 → 数据标定 → 概率」，可自证（有 AUC/Brier/校准曲线）但依赖标签质量（单站人工观测）。这是可解释性与可验证性的取舍。
  • NN 的角色：Skyglow 把 NN 当「第二个独立意见」展示分歧，且诚实声明过拟合与共用标签的非独立性；sunglow 完全没有NN，但用五因子参考模型扮演了同样的「独立旁证」角色（refGap 用 z 分数标准化后度量形态分歧）——思路巧合地一致。
证据本节所有公式、常量、阈值均逐行取自 core/model.py、core/spectrum.py、core/meteo.py、core/solar.py 与 v2/src/core/{physics,scoring,astro,forecast,refmodel}.ts、tools/calibrate.py、data/validation.json、data/model.json；「sunglow 无回测」为仓库内检索结论（README/架构文档/calib 模块均无实测标签评估），非对其不存在性的断言。

5.1 三维记分卡

5.2 结论

  1. 同源异构，不是替代关系。两者共享 sunsetbot 公开物理内核，真正分野在「算力放在哪」：Skyglow 把算力放进 Python 服务端，换来 ERA5 历史、四源并列、GRIB2 直连、NN 与全国地图；sunglow 把算力留在浏览器，换来零依赖部署、合规地图与完整产品外壳。任何一方做不出对方被物理条件锁死的那些能力（浏览器跑不了 eccodes；静态页藏不住服务端计算）。
  2. 算法层面最值得互相迁移的是「标定与验证」。sunglow 的模型是「物理量 + 手工阈值 + 固定权重」，透明度高但无自证能力；Skyglow 用同一族物理量做岭回归标定并给出 AUC 0.80 / Brier 0.12 的证据链。 sunglow 若要提升算法可信度，最短路径是把 9 因子空间接到 Skyglow 的标定管线（calibrate.py 可直接复用），而无需更换其手工模型结构。反之，Skyglow 若要提升「模型间分歧」的解释力，可借鉴 sunglow 的三路集合与 refGap（z 分数形态分歧）做法。
  3. 工程层面最值得互相迁移的是「回归体系与口径冻结」。sunglow 的 557 条断言 + docfacts + 冻结副本机制，正是 Skyglow（16 个工具脚本、依赖作者机器路径、无统一总表）最缺的；而 Skyglow 的服务端配额工程（熔断、令牌桶、TTL 缓存）也正是 sunglow 纯前端形态下做不到的。
  4. 产品策略上两者已各自找到最优形态： sunglow 作为「给任何人用的静态产品」已趋完成（且仓库自身决策文档已定 v2 为主线、V1双落继续上线）；Skyglow 作为「自托管研究版」价值在数据深度与可复现实验。若资源有限，建议维持双线：sunglow 继续做产品与地图体验，Skyglow 继续做算法标定、历史回溯与四源对照，并通过既有的架构文档保持口径互证。
证据5.1/5.2 的综合判断依据第 1–4 节全部对照表；「浏览器跑不了 eccodes」「静态页藏不住服务端计算」有仓库自证（STATIC_HOSTING.md §二.4/§二.5）；sunglow 主线决策引自仓库自身《项目架构与技术实现方案.md》§10（v2 为主线、V1双落）。
