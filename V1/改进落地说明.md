## 批次 5 · 功能（P1–P2）

### P4 降低 429 风险 / 减少冗余计费请求 —— 落地方式与原提法不同（重要）

**原提法**（方案 §4 P4）：把单点查询的 17 个样带点与地图的 107 个点**取并集合并成一次多坐标请求**，期望"首屏计费请求 7 → 2"。

**实测否定了这个提法**（`_check/tzprobe.js`）：

```
计费权重 = max(1, 变量数/10 × 时间跨度系数) × 坐标数
                       （Open-Meteo 公开说明；即**每个坐标至少计 1 次**）

坐标数口径        ：现在 3×(17+107)=372   并集后 3×124=372     → 零节省
「变量×坐标」口径 ：现在 3,603            并集后 3×124×14=5,208 → +45%
```

原因：地图侧特意把字段集压到 **9 个变量**（≤10 变量恰好落在权重 1.0 的基准档）；一旦与单点侧的 14 个变量取并集，107 个坐标的权重会从 1.0 涨到 1.4，**反而更容易触发限流**。另外并集请求要等两边都凑齐才发，会把本来 17 坐标的小请求串到 107 坐标的大请求之后，**推迟首屏主结论**的可见时间（实测该 URL 长度 2,996 字节、124 坐标虽被接口接受，但账不划算）。

**实际落地方式** —— 改为"消除真正多余的取数"：

| 子项              | 落实位置                                                                    | 说明                                                                                                                                                                                   |
| --------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ① 统一时区口径        | `_p4.js:18` `const API_TZ = "auto"`；`_p6.js:33` `const MAP_TZ = API_TZ` | 原先单点侧用 `auto`、地图侧硬编码 `Asia/Shanghai`，是两个口径。因为取样点全在中国，两者数值恰好一致，所以一直没暴露；一旦地图点位扩到境外就会**静默算错时间轴**。现在由结构保证一致，不再靠"碰巧"。实测佐证：上海两者完全一致，纽约 `auto → -14400` 而 `Asia/Shanghai → +28800` 且温度序列不同。 |
| ② 去掉按城市搜索时的强制刷新 | `_p5.js:95`：`loadMapData(true)` → `loadMapData(false)`                  | `onSearch` 原本每次按城市搜索都强制重发**整批 3×107 = 321 个加权调用**。地图数据只按**日期**索引、与查询地点无关，换城市根本不影响它，属纯浪费。                                                                                             |
| ③ 让"首屏计费请求数"可断言 | `_p4.js:26` `API_CALLS` / `:28` `apiCallLog` / `:35` `apiCallStats`     | 新增计费请求登记表，测试可直接读账。                                                                                                                                                                   |

**验证**（`_check/cdp.js` → `=== P4 计费请求 / B9 缓存上限 / 时区口径 ===`）：

```
地图一次强制取数: 3 个请求 / 321 坐标  ["forecast/107x9/auto","forecast/107x9/auto","air-quality/107x4/auto"]
按城市搜索后（地图已在缓存）: 3 个请求 / 51 坐标 / 其中大请求 0 个      ← 关键：321 个调用被真正省掉
首屏计费账目（坐标数口径）: 单点 51 + 地图 321 = 372
两侧时区口径: ["auto"]                                                  ← 单点与地图同一个口径
```

## 后续追加 · 减少额度消耗（B11 懒加载 + 429 双分类）

### 起因：算清了限流的真实原因

「接口暂时限流」不是偶发故障，是把量的口径算错了一直在发生。Open-Meteo 免费层的口径是：

- **10,000 次/天 · 5,000 次/小时 · 600 次/分钟 · 300,000 次/月**
- 计费权重 = `max(1, 变量数/10 × 时间跨度系数) × 坐标数`，**每个坐标至少计 1 次**
- **按「出口 IP」计**，不是按账号 —— 免费层没有 key，服务端无法区分调用者

单页一次的账目（坐标数口径）：

| 环节          | 算式                   | 加权调用      |
| ----------- | -------------------- | --------- |
| 单点天气预报      | 17 点 × 2 模型 × 权重 1.4 | 47.6      |
| 单点气溶胶       | 17 点 × 1.0           | 17        |
| **地图** 天气预报 | 152 点 × 2 模型 × 1.0   | 304       |
| **地图** 气溶胶  | 152 点 × 1.0          | 152       |
| **合计**      |                      | **≈ 520** |

⇒ **一天只够开约 19 次首屏**；其中地图一项占 **456/520 = 88%**。

顺带核实了几条出路：付费 Standard **$29/月** = 1M 次/月（无日限），端点换成  
`customer-api.open-meteo.com` + `&apikey=`，**参数与响应格式完全一致**；服务端 **AGPLv3 开源可自建**。

### 决策：不动「多模型」

降低用量最省事的做法是砍掉地图或砍成单模型 —— **主动不做**。「GFS / EC / 光追三路各自出结果  
再给综合」是原始需求第 2、3 条的核心，砍掉就不是这个产品了。所以只动「什么时候取」，  
不动「取什么」。

## 后续追加 · 地图局部化（B13）

> 需求原文：① 缩小地图显示范围，不再显示全国热力图，以节省查询次数；  
> ② 热力图跟随搜索查询联动，仅显示查询地点及其周边区域；③ 说明改动涉及的逻辑与影响范围。  
> （修改前已按要求备份到 `_backup/before-local-map/`。）

### 起因：地图那张图的面积，就是它的账单

局部化之前，地图是**固定 152 个全国城市**：不管用户在漠河还是三亚，一次地图取数都  
是 152 × 2 套模式 + 152 × 气溶胶 = **456 个加权调用**（免费层按出口 IP 每天 10,000 次）。  
也就是说，"打开地图"这一个动作的代价与用户所在位置、是否看得见那些点**完全无关**。

而霞光这个问题的答案，只在几百公里尺度上才有决策价值：一张全国图会把 2,000 km 外的  
漂亮云系也涂成红色。把范围收小既贴近用途，又直接把账单按面积砍下来。

### 参数（由用户从候选中选定）

| 参数                      | 取值                     | 说明                                   |
| ----------------------- | ---------------------- | ------------------------------------ |
| 覆盖半径 `MAP_RADIUS_KM`    | **500 km**             | 相当于"邻省 + 周边地级市"，一个周末出行的决策范围          |
| 采样间距 `MAP_GRID_KM`      | **120 km**             | 必须显著小于云系空间尺度（几百 km），否则插值出来的场只是几个孤立圆盘 |
| 取数时机                    | **自动跳转但仍手点加载**         | 视口跟随查询，但数据仍由用户显式触发 —— 保持 B11 的懒加载纪律  |
| 沿用阈值 `MAP_KEEP_KM`      | **120 km**（= 一个采样间距）   | 见下文「为什么不是任何移动都重取」                    |
| 跨地点缓存上限 `MAP_CACHE_MAX` | **6 条**（= 2 地点 × 3 日期） | 补 LRU 够不到的那一类条目                      |

**为什么是等距经纬网格，而不是"500 km 内的城市表"**：城市分布本身东密西疏 ——  
按"附近的城市"筛，东部一次能筛出七八十个、西部十几个，**额度变得无法预期**；  
网格布点与地理位置无关，每次查询的花费是同一个数（57），用户和开发者都算得清。

**判圆为什么用公里偏移而不是度数偏移**：经度每度对应的实际距离随纬度收缩。  
直接拿 `dLa/dLo` 比长度会把圆盘压成椭圆 —— 在 50°N，同样度数的经度跨度只有纬度跨度的  
0.64 倍。实测 52.3°N 与 31.2°N 的经度跨度比为 **14.11° / 10.09° = 1.40**，正是  
`cos31.2° / cos52.3°` 的倒数。

### 为什么不是「任何移动都整批重取」

第一版实现是"地点一变就清空"。它能满足需求②字面意思，但有一个直接的反例：  
地图提示里有「**在此处精细查询**」按钮，用户点了它，查询点就挪到了点击处。  
如果点击处离网格中心只有 34 km 也要清空重取，那么"看到某处颜色漂亮 → 点进去看细节"

开着 `#autoMap` 时更糟 —— 每次微调经纬度都自动重取。

### 一个被顺手发现的缺陷：localStorage 单向增长

`MapMod.data` 的 LRU（B9）**只按日期计数**（上限 3），而局部化之后 localStorage 的键  
多了一维坐标。于是出现了一类 LRU 管不到的条目：**换地点以后，旧地点的键再也没人删** ——  
`mapDataTouch` 淘汰时用 `mapKeyOf(old)` 拼的是**当前**坐标，根本命中不到旧地点的键。  
用户每走一个地方就留下最多 3 条（实测 57,083 字符/条 ≈ 57 KB），**单向增长到 5 MB 配额耗尽**，  
之后写缓存开始静默失败（只留一行 `mWarn`）。

修法是补一道**跨地点**的总闸门 `mapCacheSweep()`：按写入时间保留最近 `MAP_CACHE_MAX = 6` 条，  
且**当前地点的一条都不删**（马上要用的正是它）。6 = 2 个地点 × 3 个日期，  
既给"返回上一个地点"留了命中机会（这正是键里带坐标的收益），又只有约 0.35 MB。  
调用点两处：`mapCachePut` 写完立刻收、`mapOnPlaceChanged` 换地点时收。

### 缩放探针的两处修正（为什么不是"把容差调大"）

**① 三条断言因取样点过时而失败，不是缺陷。** 21 项失败全部来自"取样城市在值场外"。  
改为动态取样后剩 1 项：淮安市附近 @338 km 在 zoom 4 档读到 `rgb(232,51,21)`、  
期望 `rgb(230,47,20)`，绿通道差 4（容差 3）。

查证过程（不是猜）：条带画布的内容由 `putImageData` 逐像素写入，**与缩放无关**；  
`fitRaster` 只改 CSS `transform: scale()`。实测各档 scale 为 zoom 4→**1.14**、  
zoom 6→**4.56**、zoom 12→**291.28**，全是放大档 —— 所以不是重采样混合。

真正的原因是**投影取整落到相邻格**：`exp` 由 `fieldValue()` 取**最近格**算出，  
而屏幕像素走"投影到容器像素 → 反查画布像素"，两级取整都可能偏一格。  
采样间距 120 km、模糊半径 89 km 之下，相邻格（11 km）的颜色本就能差几级 ——  
**这个 11 km 的偏移远小于数据自身 120 km 的分辨率**，对用户不可见。

所以正确期望不是"唯一一个颜色值"，而是**以该点为中心的一格邻域内出现过的颜色**  
（把这一格的画布像素取出来做成通道包围盒）。盒外的像素则一定是真错位  
（原缺陷量级 200）。同时把第 4 条断言从"颜色跨缩放一致"改成  
**"透明度跨缩放一致"** —— 它更直接地对应原始反馈（"过度放大时颜色完全消失"，  
实测原缺陷是 alpha 209 → 0 的崩塌），而颜色一致性已由第 2 条在每个缩放档上覆盖。

**② 顺带修掉探针自身两个静默错误**（都属于"测试骗自己"那类）：

- 在 Node 的模板字符串里写 `/scale\(\s*([-\d.]+)\s*,\s*([-\d.]+)\s*\)/`，  
  模板串会把 `\s`、`\(` 这类非法转义的反斜杠**吃掉**，正则于是永不匹配 ——  
  而"读不到缩放比"又恰好落进兜底分支，不会报错。改用 `indexOf` 切字符串避开转义陷阱。
- 在模板串的注释里写反引号会把模板串提前闭合，直接语法错误。

### A1 地图样带与单点同构

**症状**（用真实数据实测，广州 2026-10-09 晚霞）：同一个点、同一时刻，
结论卡说 P/Q/I = 25.6/27.8/26.6，地图中心说 22.8/26.8/24.6，**ΔI = −2.0**。
用户看到的是两张互相打架的图。

**根因不是"样带点数少"这么表面**，而是 `analyseTransect` 里的步长依赖：

```js
step = transect[1].d − transect[0].d        // 旧地图只有 2 点 → step = 250
dFar = 最末点.d + step                       // 开边界 → 250 + 250 = 500 km
```

单点用的是 `TRANSECT = [0,25,…,400]`，同样口径算出 `400 + 25 = 425 km`。
**步长不同 ⇒ 同一片云被算出不同的云边界距离** —— 两个入口因此对同一片云给出不同的几何结论。

**改法**：地图样带改成与单点**完全同构**的 17 点（同一张 `TRANSECT`），
`once(ci, evMs, om, az)` 的 `trOf` 逐点构造。取值来源仍然不同
（`d=0` 是本网格点自己的真实值，其余 16 点由云场 IDW 推求），
但那只是"真实样带 vs 插值样带"的**精度差**，不再是**口径差**。

- `MAP_AZ_KM` 由写死的 250 改为 `TRANSECT[TRANSECT.length-1]`（= 400）
- `MAP_CACHE_PREFIX` **v4 → v5**（值场数值变了，旧缓存必须作废）
- 删除通用的 `idwSample()`，拆成 `idwPlan(目标点)` + `idwOf(plan, vals)`

**性能坑（必须记）**：权重只跟目标点位置有关、与变量无关，所以按「网格点 × 样带点」
预算一次、4 个变量共用。若照 `idwSample` 每变量各算一遍，
57 点 × 16 外点 × 4 变量 × 2 时段 ≈ **150 万次球面距离**（每次含三角函数），
会明显卡住取数；预计算后降约 **23 倍**。

**效果**：ΔI **−2.0 → −0.9**（达到"≤1.0"的验收标准）。剩余 0.9 是"真实采样 vs IDW 插值"的
不可避免的精度差，不是缺陷。

### 一个被探针抓出来的真实缺陷：同名函数「静默覆盖」（本批最重要的教训）

三个内联 `<script>` 块共享同一个全局作用域。`_p4/_p5/_p5b` 合起来是**块 0**，
`_p6.js` 是**块 2**，块 2 后执行 —— 它的 `function` 声明会**悄悄顶掉块 0 的同名函数**，
既不报错也不警告。（反过来，`const` / `let` 重复会抛 `SyntaxError` 让整个块不执行，
那个更响、反而安全。）

**踩到的实例**：`_p6.js` 里早就有 `function confOf(km)` —— 那是**地图「可信度纱」**用的，
判的是"离最近采样点多远"。本批给单点新增的分歧档位函数最初也叫 `confOf`，
于是 `_p5.js` 里写的 `confOf(dvI)` 实际跑的是"距离 → 可信度"那个版本：

- 结论卡徽标显示成 **「可信度 较高 · 距最近采样点 11 km，插值可信 · undefined」**
- 分歧提示的档位因为 `conf.key` 不存在，**全部 fallback 成 warn**
- 徽标颜色取 `cf.color` = `undefined`，整枚徽标失去了档位辨识度

**为什么值域断言没抓到**：被顶掉的函数**返回值结构完全合法**（`{lv, cls, txt}` 对 `{key, lv, color, txt, hint}`），
只是语义完全不对。值域断言看"有没有值"，看不出"值是从哪来的"。

**抓它的是 `cdp.js` 里新写的那条** —— 断言 `r.conf` 必须是 `ENS_CONF_BANDS`
里的**同一个对象引用**（`indexOf(r.conf) >= 0`），并要求 `confOf !== ensConfOf`。
引用相等对这种"被别的函数顶掉"是一击必中的：顶掉之后 `r.conf` 来自另一个数组，
引用必然不等。

**处置**：单点这一套一律加 `ens`（ensemble）前缀，与既有的 `W_ENS` 同族；
`ENS_CONF_BANDS` 的注释里写明了这次事故，并留下规矩 ——
**凡是在 `_p4/_p5/_p5b` 里新增全局函数，先 `grep _p6.js` 再命名**。

### 本批在探针侧修掉的三处「测试骗自己」

都不是产品缺陷，但都会让"全绿"变成一句没有依据的话：

1. **`cdp.js` 恒 `exit 0` —— 一次真实的 FAIL 被报成了 9/9 全绿。**
   它的失败文案是 `FAIL 下一批存在未通过的项`，既不含 `FAIL 计数` 也不含 `失败 N 项`，
   于是 `all.py` 的**退出码判定与文本兜底两条路都命中不了**。
   → 现让 `cdp.js` 包一层 `console.log`，登记所有以 `FAIL` 开头的输出行，
   末尾打 `FAIL 计数: N` 并**用它作退出码**（两条通路都能抓到）。
2. **`localgrid.js` 把 `sunsetbot.map.v4.` 写死** —— A1 有意升到 v5 后它开始误报。
   → 改为断言"前缀形状合法 **且 ≥ v5**"。把版本号写死在探针里等于每批都要改一次；
   真正该钉的是"不低于产生这次语义变更的那个版本"。
3. **分享卡断言用固定 `sleep(500)`** —— 1560×800 的 PNG 实测约 800 KB，
   机器一忙编码就超过 500 ms，这条断言于是时灵时不灵（实测灵过一次、也失灵过一次）。
   → 改为轮询到条件满足或超时 10 s。**探针里不要用固定 sleep 等异步结果。**

还有一处属于**断言写法**的改进：新段落不再把十几条串成一个巨型 `&&`，
而是写成 `{名称: 条件}` 对象、并打印未通过项的名字 ——
此前挂一次只报"未通过"，白跑一趟三分钟才定位到是 `/\\.png$/` 写错了
（把模板串里的转义习惯带到了 node 侧正则，实际要求字符串含字面反斜杠）。

### 过程中发现的一个真缺陷（方案里没预料到）

`sweepPrefix()` 原策略是"**豁免当前地点**的条目"，这对地图是安全的（地图另有
按日期的 LRU，上限 `MAP_DATA_MAX=3`，豁免当前地点还能保证"切回上一个日期"不用重取）。
但单点缓存**没有任何别的淘汰机制** —— 一个用户在同一城市里翻 18 个日期 × 2 个时段
就是 36 条，而实测每条约 **754,398 字符**（`_check/pointcache.js` 实测），
合计 ≈ **27 MB**，localStorage 配额会在几秒内写满、之后所有缓存静默失效。

→ 处置：`sweepPrefix(prefix, max, keepMine, protect)`，两个键族取**不同**的
`keepMine`（地图 `true` / 单点 `false`），并由写入者把自己刚写的键作为 `protect`
传进来。`POINT_CACHE_MAX = 4` 因此是**实测定的**、不是拍的。
另新增 `dropStalePrefixFamily()`：升版本号时清掉上一版的残留（那些键再没人读、
也再没人删，只会静静占着配额 —— 就是硬约束 14 那类故障）。

# 第七批 · 地图模块口径对齐与方位参照（2026-10-11）

完整方案与逐项实测见 **`地图改进方案.md`**（含 §十三「执行结果」表）。这里只记
**为什么这么改**与**踩过的坑**，不重复数字。

## M1-1 掩膜口径与排行榜口径必须同批对齐

**这两条是一件事的两面**，分开做都会出事：

- 只做「榜单过可见性」而不放宽掩膜 ⇒ 三亚**整榜消失**（它的前 8 全在海上）；
- 只放宽掩膜而不过滤榜单 ⇒ 边境城市的榜仍会列到境外、画布外的点。

根因是 `buildLandMask` 的位图只有**中国陆域**（省界多边形），因此它把**全部海域**一并裁掉；
而 `cnMaskOn()` 在查询点境内时无条件启用。B13 只放开了"查询点在境外"这一半，
漏了"**查询点在境内沿海**、网格伸到海上"这一半 —— 而 `MAP_AZ_KM=400` 的样带本就是
沿朝/晚霞方位量的，**答案就在近海**。

修法（甲）＝位图**可分离定距膨胀**（`MASK_KEEP_KM = 300`，先纬度后经度、
经度窗口按 `cos(lat)` 折算）；（乙）＝新增 `mapVisibleAt(f,lat,lon)` 并在 `renderRank` 里过滤。

两个坑：

1. **`mapVisibleAt` 必须读色面像素，不能读几何。** 第一版读 `g.land[o] > 0`，
   于是多列了一个"land=1 但被 `boxBlur(mask, FIELD_BLUR=8)` 抹到阈值以下"的点
   （三亚榜前 8 的「河内 南 440 km」，栅格 3×3 邻域最大 12、画布 0）。
   判据只能是 `f.img[(r*f.cols+c)*4+3] > 0`。
2. **`renderRank` 不能读 `MapMod.field`。** `paintMap` 在"无可用数值"路径上提前
   `return`，那时 `MapMod.field` 还停在上一次的对象上。必须由 `paintMap` **传参**本次的 `fld`。

**刻意不用 ETOPO1 判海**：产物里已有 0.5° 高程栅格（零网络），看着免费，但实测 10 个已知点
**判错 2 个**，且错的都是"真海判成陆"（上海外海 60 km 读 0 m、吐鲁番盆地读 245 m）——
前者的后果正是"放宽失效"。0.5° + 双线性把陆地高程抹到海上，**岸线外 0–60 km 那条带
判错方向恰好最坏**。

掩膜**不进缓存**（`mapCachePut` 只存 `{ts,obj}`，几何是内存派生的）⇒ 不必升版本号；
`localgrid.js`（只测开关）/ `zoomprobe.js`（手工色面不含掩膜）/ `cdp.js`（纱断言读的就是
已掩膜 alpha，自动跟随）都不用改。

## M1-3 提示卡被裁

`.tip` 永远向上翻转、`top` 兜底在 90 px ⇒ 指针 y=100 时卡片顶边落在容器 **−178 px**。

# 第八 / 九批 · 视觉改造：从"一团雾"到"有边界的预报图"

> 与前面各批不同：这两批的动因不是缺陷或额度，而是**观感**——
> 用户反馈"地图看上去怪怪的"，要莉景天气 App（深色底、离散色斑）与
> sunsetbot 网站（等值线 + 分级填色 + 经纬网）那种效果。经确认走**「结合」**：
> 分级填色 + 干脆边界 + 等值线 + 经纬网；深色底图做成可切开关、默认浅色。

## 诊断：先把"怪"量化（第八批）

新增 `_check/styleprobe.js`（不进 `all.py` 序列；用只随位置缓慢变化的合成数据，
模拟"只有局部有信号"的真实分布）。改前实测（广州，栅格 143×131 ＝ **1464×1449 km**）：

| 指标 | 实测 | 含义 |
| --- | --- | --- |
| 地图像素 / 栅格格 | **4.56** | 一格格子 ≈ 4.6 屏像素 |
| 完全不透明（alpha=209）占比 | **28.9%** | 七成色面是半透明的 ⇒ 发虚 |
| 到最近采样点距离 | P50 **69** · P90 **204** · max 240 km | 中位像素离最近采样点已 69 km |
| 淡出带宽（屏幕） | **≈180 px** | 一圈大雾 |
| 色面内不同 RGB | **168** | 连续无级、没有一条边界 |
| 数值分布 P25/P50/P75 | **44.7 / 48.4 / 54.1** | 中间 50% 的格子只跨 **9.4 分** |
| 可信度纱覆盖 | 已上色面积的 **46.2%** | 勾上像渲染错误 |

五条根因：① 取景比采样区大一圈（采样网格直径 ~1000 km，栅格却 1464 km，
边界是 57 个半径 240 km 圆盘的并集 ⇒ 扇形缺口）；② 数值被插值压扁，色阶却按
**点**的值域拉伸 ⇒ 大部分区域落在一个很窄的色段；③ 可信度纱是整片实心灰；
④ 色阶低端是白色，与浅色底图分不开（这才是"底图压暗"补丁存在的原因）；
⑤ `FIELD_BLUR=8 格（88 km）> FIELD_FULL=75 km`，模糊核比实心半径还大。

**参照物在做同一件事：把连续场变成有边界的东西。** 我们当时是"连续渐变 + 白色低端"，
所以只能看成雾。

## 第八批的改法

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 色面边界 | 到最近采样点距离 240 km 截断 | **采样点凸包**（`buildHull` 单调链）+ `FIELD_OUT_KM=70` 羽化 |
| 栅格 `FIELD_STEP` | 0.1°（11 km） | **0.05°**（5.5 km）—— 分档能落地的前提 |
| 模糊 `FIELD_BLUR` | 8 格（88 km） | **2 格**（11 km） |
| 不透明度 | 0.82 | **0.9** |
| 色阶 | 256 档连续 | **`N_BANDS=7` 档填色**（`bandOf`/`bandColor`/`bandGradientCss`） |
| `FIELD_FULL` | 75（兼作色面边界） | **90**，只作"外推"分档阈值，与边界**解耦** |
| 候选搜索半径 | `FIELD_RANGE=240` | **`FIELD_REACH_KM=120`**（`MAP_IDW_MAX`/`TIP_RANGE_KM` 同源） |
| 深色底图 | 只有 `.dimbase` 压暗层 | 复选项改「深色底图」；`.mapwrap.dark` 给 `#map` 与**全部叠加层**套同一个 `invert(1) hue-rotate(180deg)` |

「深色底图」能不动色面像素的原理：叠加层都在 `#map` **子树内**，父层的 filter 会先把整棵
子树翻一次，子层再套同一个 filter 就恰好抵消（`invert∘invert=id`、
`hue-rotate(180)∘hue-rotate(180)=id`，且两者仿射线性、与 alpha 合成可交换）。
**绝不能加 `contrast`/`saturate`**（非对合）。

复量（广州，合成数据）：栅格 **217×200 · 1111×1106 km**；完全不透明占比 28.9% → **50.6%**；
到最近采样点 P90 204 → **72 km**；可信度纱覆盖 46.2% → **1.2%**；
色面内不同 RGB 168 → **8**（7 档 + 未上色的 0,0,0）；屏上淡出带宽 ≈180 → **≈32 px**。

## 顺手抓到的真缺陷：条带接缝（第八批）

`fitRaster()` 原先给每条带加 **0.75 px** 高度去盖亚像素缝隙（注释写着"无副作用"）。
**这个"无副作用"是错的**：色面是半透明的，重叠那一行会被 alpha 合成两遍
⇒ 浅色底图上一条更深的横线。旧配色（28.9% 不透明 + 88 km 大模糊）把它摊没了；
换成凸包 + 分档后不透明占 50.6%，它就显形了（实测该行亮度比邻行低 **7.7**，全图只此一条）。
修法：先投影出所有条带上下沿，**统一取整到设备像素**（`round(y*dpr)/dpr`），
底沿直接取"下一条的顶" ⇒ 缝隙与重叠同时消失，不需要任何补丁。

## 第九批 · 等值线 + 经纬网

**等值线必须独立成层。** 最初想直接描进色面栅格（省一层、自动随 alpha 淡出），
否掉了：色面像素 ↔ 数值的**单值映射**是 `zoomprobe` 像素级断言守护的性质
（"看图反查数值"），在栅格上描线会把它打掉。故新增 `.clayer`（z-index **2**，
色面 1 之上、可信度纱 3 之下 —— 纱盖住的恰是外推区，那里的线本就该被压淡），
图层号整体重排 `conflayer 2→3 / azilayer 3→4 / mlayer 4→5 / pinlayer 5→6 / mload 6→7`。

- 等值线：与色面**同 per/count/栅格尺寸**，`fitRaster` 里直接复制色面条带的 transform
  （不必再投影，也绝不可能错位）。判边＝**4 邻格里任一档位不同就描**。无数据格与色面
  `alpha=0`（被掩膜裁掉）的格都不描 ⇒ 线在掩膜边界与羽化尽头自然断开。
  线 alpha = `CONT_ALPHA × 色面 alpha / 255` ⇒ 外推区里线跟着淡出。
  > **勘误（第十批）**：这里原写"只描第一个不同的那一格 ⇒ 线宽恒 1 格"，**与代码不符**。
  > 代码是四个邻格逐个查、任一档位不同就描 ⇒ **两侧都描**。第十批用
  > 「墨迹像素数 ÷ 边界长度」重新量过：K=1 时线横跨 **1.46 格 ≈ 3.32 px**
  > （不是 1 格 2.28 px，也不是 2 格 4.56 px —— 直角边界上确实是 2 格，
  > 斜/波浪边界上两侧的墨迹会互相重合，故落在两者之间）。
- 经纬网：**不猜投影公式**。联调环境的替身是等距圆柱、真机是墨卡托，两者纵向伸缩完全不同；
  只依赖 `projectToContainer` 的**单调性**做二分（y 随纬度递减、x 随经度递增），
  对容器四边各求一次边界，再对区间内整数度逐条精确投影 —— 两套投影下都成立。
  1° 一档；线落**整像素中心**（`Math.round(y)+0.5`，否则 1px 线被糊成 2px 灰带）。

`mapaudit.js` 新增 I 段 5 条具名断言（12 → **18 条**）。最有价值的一条：
**色面不透明区（alpha≥200）必须全部落在 7 个档位色 ±2 内** ——
实测 **22,199 个不透明像素、0 个越界**，正面证明等值线一个像素都没混进色面。

# 第十批 · 等值线做细，最后换成了矢量（2026-10-11）

用户一句话：**"等值线做细一点"**。做完之后又说了一句：**"等值线还是粗"**。
这个"还"字把两条路都逼出来了 —— 第一版是调参，第二版是换渲染方式。

## 一、先把"粗"量化，否则不知道该调什么

"粗"不是描边参数问题。线是**逐格**画的位图，**线宽 = 判边用的格子有多大**：

| 量 | 值 |
| --- | --- |
| 栅格 `FIELD_STEP` | 0.05° |
| 该格在默认取景下摊到屏幕 | **2.28 px** |
| 判边规则（4 邻任一档位不同就描） | 两侧都描 ⇒ 横跨约 1.46 格 |
| ⇒ 第九批的线**可见宽** | **3.32 px**（芯 ≈ 2.0 CSS px 的近黑色） |

顺带勘误第九批文档里那句"只描一侧 ⇒ 线宽恒 1 格"——**与代码不符**，代码是四个邻格
逐个查、任一不同就描，两侧都会描。

还有一个更基础的错：量"线宽"时不能拿"一格像素有多大"当答案。真正要量的是
**可见宽度 = 墨迹覆盖面积 ÷ 折线总长** —— 这个量才与线方向无关
（水平行程在竖线上量得准、在横线上就是无穷大）。

## 二、第一版：值场超采样（`CONT_SUPER = 2`）—— 有效，但不彻底

线的粗细分两种做法，只有一种对：

- ✗ **升采样"档位"**：档位是离散的，放大它只是把台阶放大，边界位置仍停在原格。
- ✓ **升采样"值"**（`f.vals` 双线性 ×2，**再** `bandOf` 取档）：值场连续、不造假数据，
  档界位置精确到半格。

`CONT_SUPER = 2` ⇒ 可见宽 3.32 → **1.64 px**。三档实测（同取景、同合成数据）：

| `CONT_SUPER` | 线横跨 | 可见宽 | 观感 |
| --- | --- | --- | --- |
| 1（第九批） | 1.46 格 | 3.32 px | 粗色带 + 明显台阶 |
| 2 | 1.44 格 | 1.64 px | 细一些，但**还是粗** |
| 3 | 1.46 格 | 1.11 px | 更细，可开始发虚（同 alpha 下越细越淡） |

**但用户说"还是粗"，而且他是对的。** 实测横截面：改完 K=2 之后，线的深色芯
仍有 **4 个设备像素 = 2.0 CSS px**。更要命的是这条路**治不了根**：
**线宽仍然绑在栅格上**，放大 4 倍线就粗 4 倍（第九批就登记过这条"还没做"）。
继续加 K 只能让线更淡，不能让它更细 —— 因为"多细"的上限是屏幕像素，
而栅格化没法表达比一个栅格更细的结构。

## 三、第二版：屏幕空间矢量描边（最终采用）

把"画线"拆成两件**互相独立**的事：

1. **几何**（只算一次，随值场）：marching squares 在**栅格坐标**下抽出档界折线；
2. **渲染**（每帧，随取景）：把顶点投影到**容器像素**，用**固定的 `CONT_PX = 1`** 描边。

于是线宽是一个屏幕常数，与栅格分辨率、与缩放都无关。放大 4 倍，线还是 1 px。

### 3.1 插值必须在**值场**上做，不能在**档位**上做

这是本轮踩到的第二个坑，比线宽更隐蔽：第一版矢量实现直接拿 `f.band`（整数 0..6）
当标量场去抽 `level = k + 0.5`。结果 `(t − v0)/(v1 − v0)` 恒等于 ±0.5 ⇒
**交叉点永远落在格边中点**，画出来是一条**贴着格子走的折线**，放大后满屏直角台阶。

改成在 `f.vals` 上找"档界对应的那个值"（`(k+1)/N_BANDS × 100`，`CONT_LEVELS`），
交叉点才是真实插值出来的位置。放大的对比图里，改之前是一串折角，改之后是光滑曲线。

### 3.2 投影复用色面那一次结果

等值线的几何是"栅格坐标"，要变成容器像素就得知道每个条带的仿射变换。
色面已经在 `fitRaster` 里算过一遍了（`rect[]`），等值线直接用**同一份**：

```
sx = rect[i].x + gx · rect[i].w / cols
sy = rect[i].ty + (gy − rect[i].r0) · rect[i].h / rect[i].h0
```

（`r0` 是这条带在栅格里的起始行，本轮给 `buildStrips` 补上的。）
这样线必然落在色面的档界上，不可能错位；而**线宽是屏幕像素常数**，
所以两件事第一次真正解耦了。

### 3.3 保留下来的老性质

- 四角任一格无数据（NaN）⇒ 整格跳过，线在数据边缘断开；
- 四角色面 alpha 平均为 0 ⇒ 整格跳过 ⇒ 线在掩膜外与羽化尽头自然消失，不悬空；
- 每段带一份**所在格的色面 alpha**，描边时按它分 **16 档**（同一档只 `stroke()` 一次，
  省掉几千次状态切换）⇒ 羽化区里线跟着淡出。

### 3.4 顺带解决的老账

第九批登记的"等值线在高缩放档会随色面一起变粗"**一并消失** ——
它不是被单独修的，而是这个架构里根本不存在了。实测：默认取景与 z8，
线的横截面完全一致。

## 四、探针：一次大改，加三个坑

`mapaudit.js` I 段整段重写（仍是 **8 条**，总数保持 **20 条**）。

**① 画布＝容器分辨率**（结构性判据）：`cv.width === round(host.clientWidth × dpr)`。
这是"线宽与缩放解耦"的前提，必须正面守住。

**② 墨迹不悬空**：线的每个像素都要落到色面真的上过色的地方。探针自己重建投影
（读 DOM 的 `getBoundingClientRect`，**不读**实现里的 `rect`），顺带把"线到底画在
屏幕哪个位置"也验了一遍。

**③ 可见宽度 = 墨迹覆盖面积 ÷ 折线总长**。这条量了四次才对，四个坑都值得记：

| 错法 | 实测 | 为什么错 |
| --- | --- | --- |
| `Σalpha/255 ÷ 总长` | 0.60 px | ① 总长含**画布外**的段（墨迹被裁了、长度照算）；② `alpha/255` 量的是**墨色浓度**（线本身 alpha≈0.67）不是几何覆盖率 |
| 同上，改只在"色面全不透明区" | 0.82 px | 用 `max(alpha)` 当归一标尺 ⇒ 不同档位的线在交叉处 **alpha 合成**（156 压 156 → 216），几个交叉点就把标尺抬高 |
| 改用直方图峰 | 测不出 | `dpr=1` 下斜线的大多数像素只被**部分**覆盖，alpha 分布弥散，根本没有峰 |
| **`Σalpha ÷ (完全覆盖像素应有的 alpha) ÷ 折线总长`** | **1.07 px** | ✓ 标尺由 `CONT_ALPHA` + 分档规则算出（`round(CONT_ALPHA × (档+0.5)/16)`），还原出的是**几何面积** ⇒ 改 `CONT_ALPHA` 不会让宽度读数变，改线宽才会 |

另外"色面全不透明"的阈值**取实测峰值 − 2，不能写死 255**：海陆掩膜边缘被 `boxBlur`
抹过，整张色面的 alpha 峰值只有 **230**，写死 255/250 会一格都取不到。

# 第十批之后 · 第三轮方案（2026-10-11，纯分析 + 一次回退）

对应 `下一步方案3.md`。本轮**没有留下任何行为改动** —— 唯一动过代码的批次最后回退了。

## 凸包折角：两轮实施后判定**不修**

- **第一轮（数学前提不成立）**：原设想"包外距离减常数 r（Minkowski 和）"。实测
  `max over 半平面` **不是欧氏距离**，而是切比雪夫型：内角 135° 的顶点外侧只到真值的
  **0.924 倍**（90° 时 0.707 倍）⇒ `d = c` 的等值线在顶点处是两条平行线的**交点**（尖角），
  减常数只是把它整体外移，**磨不圆**。
- **第二轮（正确但无效）**：改成"点到**线段**距离取 min"（精确欧氏距离）。等值线确实成了
  外侧等距线，但**实测收益≈0**：实拍逐像素最大通道差 **10**（差 >5 的像素占 **0.052%**）、
  alpha 场最大差 **0.069**、差 >0.05 的格点仅 **0.11%**。理论位移
  `70 × (1/0.924 − 1) = 5.8 km ≈ 4 px`。
  **根因**：凸包尺度 500 km（短边 240 / 长边 509）远大于羽化带 70 km —— 顶点方向能动的最多 5.8 km。
- **第三轮（纸上推演，否决）**：改用**圆形**色面。实算：圆必须 **≥495 km** 才能覆盖最外圈采样点
  （否则图钉落在色面外）；但 **≤440 km** 才能保证羽化带内 `dmin ≤ 120`（否则造出真环带）—— **不可兼得**。
  凸包恰好让最外圈采样点落在自己的边界上（`alpha = 1` 区），这是任何圆都做不到的。

**结论**：色面外缘的八边形是**凸包语义的固有形态，不是缺陷**。代码**已回退**，
回退后实拍与基线**逐像素差 0**（md5 层面行为一致）。只保留三处**事实性**注释更正：
"12 边形 → 去共线后八边形（`hull.length` 浮动 8/10/12）"、"32 px → 46 px"、
`FIELD_REACH_KM` 的余量改成实测值。

## 批次 B1 · 数据范围边界线：**已落地**（且比方案多一道闸门）

**为什么做**：档 0/1 的浅黄接近白，对浅色底图的 WCAG 对比度只有 **1.05** ⇒ 低值区
"到底算过没有"读不出来。改色阶**无解**（见上），所以改成把**范围本身画出来**。

**做成了什么**：在等值线层（`.clayer`）沿**采样点凸包**画一条**虚线**（`setLineDash([5,4])`、
`CONT_RGB` 同色系、alpha 0.42、固定 1 px）。画在凸包本身而不是羽化带外缘 —— 那里
`alpha = 1`，线才看得见，而且它**就是那条分界**（线内＝插值、线外到色面淡出处＝外推）。
两条图例文案同步补了说明。

**方案漏掉的那件事（实测才暴露）**：方案写"再加一条沿色面外缘的线"时**没考虑海陆掩膜**。
第一次实现照几何原样连成整圈，跑回归时那条既有的 `等值线墨迹不悬空` 断言立刻从 0 变成
**`悬空 81 处`** —— 因为掩膜会**成片删掉色面**，而**沿海城市的凸包大半伸进海里**
（I 段跑在三亚，凸包 500 km 半径的南/西两片全是南海）。照几何连线就必有一段
**浮在没有颜色的海面上**，而那正是等值线层早就立下的纪律要拦的东西
（`buildContourGeometry` 里 `a4 < 1 → continue`："色面这一格没上色 ⇒ 线不悬空"）。

⇒ 实现改成**沿每条边采样、只画色面真的有像素的弧段**（与等值线同一条纪律）：
采样在**容器像素**里做（与等值线同一套 `rect`；注意 `rect[i].h0` 只是**本条带**的行数，
要加 `r0` 才回到全栅格行号）、步长 **1 px**、**每条弧段单独 `beginPath()`+`stroke()`**
（同一路径反复 stroke 会让 alpha 叠加变深）。

| 指标 | 不裁断（第一版） | 裁断后（落地版） |
| --- | --- | --- |
| `mapaudit` 悬空 | **81 处** | **0 处** |
| 画出的采样点 | — | 1050（步长 1 px） |
| `mapaudit` 断言 | 20 条，1 红 | **22 条全绿** |

**顺带查清一个文档错误**：§七 那条"12 边形 → 8 边形"的更正经实施 B1 才发现**也不准确** ——
"8"是用**精确整数坐标**算的，运行时走的是**经纬度往返**，与长边**严格共线**的网格点弹不弹
只看浮点噪声 ⇒ 实测同一份代码 **大连/乌鲁木齐 8、三亚 10、其余 12**（画出来是同一条八边形）。
故探针断言写成 `edgePts === hullN`（有几个连几个），**不写死数字**。

**探针**：`mapaudit.js` I 段加两条具名断言（`hullN >= 3 && edgePts === hullN`、`edgeIn > 0`），
并把 `MapMod.edgePts` / `edgeIn` 暴露给探针。**"不悬空"不再单独量** —— 那条等值线断言
与 B1 共用一块画布，它本身就是端到端证明。

**实拍**：`_check/scout-edge.png`（默认取景）、`_check/scout-edge-zoom.png`
（放大到凸包西北长边：虚线正好落在"插值/外推"分界上，白色羽化在它外侧）。

## 批次 C1 · 经纬网开关：把 `gratOn` 的双重语义拆开

**为什么要拆**：`MapMod.gratOn` 兼两职 —— ① `drawGraticule()` 派生的"网画出来了没"；
② `gridOn()` 读它决定 `.clayer` 显不显示。直接加一个开关会坏在两处：
`drawGraticule` 里那句 `if (!MapMod.gratOn) { MapMod.gratOn = true; refreshGrid(); }`
会在每次 `fitRaster` 时把用户的选择**静默打开**；`gridOn()` 也会拿它误判等值线层可见性。

**落地**：

| 位置 | 改动 |
| --- | --- |
| `MapMod.gratUser` | 新增，用户偏好，默认 `true`（**不持久化**，见下） |
| `drawGraticule` | 入口加 `MapMod.gratUser &&`；`!vb` 分支里**显式 `svg.style.display = "none"`**；开时恢复 `""` |
| `setGratUser(on)` | 新增，**唯一入口**：写偏好 → `gratSig = ""` → 立刻 `drawGraticule()` |
| `gridOn()` | **不改** —— `gratOn` 已含 `gratUser` 语义，再套一层是重复判断 |
| `tpl/template.html` | `.maptool` 里加 `#showGrid`（默认 `checked`） |
| `_p5.js` | `initUI` 里 `#showGrid` 的 change 事件 → `setGratUser` |

**两处偏离原方案**（`下一步方案3.md` §5.1）：

1. **不持久化**。另外 4 个图层开关都不持久化，项目也没有通用偏好存储机制；
   为其中一个单开一条 `localStorage` 通道会造成"只有它能记住"的怪异体验。
   刷新后回到默认（开），与既有行为一致。
2. **`gridOn()` 不改**。既然 `gratOn` 已是 `gratUser && 图面可用`，外面再判一次 `gratUser` 是冗余。

**只有实测才会暴露的一个点**：关掉时**不能只靠 `.clayer` 的 `.on`** ——
它的语义是"等值线或经纬网有其一即显示"，等值线还在时整层不会被关掉。
必须显式隐藏那张 SVG。反过来，"关→开时视野没动"会被 `gratSig` 闸门直接 return、
`display` 永远停在 `none` ⇒ `setGratUser` 必须让签名失效。这两条现在都由 `mapaudit` J 段钉住。

**实测**：`.maptool` 加第 5 个复选框后 **129 px / 3 行不变**（基线同为 129 px / 3 行 / 9 个控件，

## 手机端适配（真机反馈 → 已落地）

来源是真机截图上的两个问题，与前面几批"方案驱动"的不同，这一批是**现象驱动**的，
所以先做的不是改而是**量** —— 写了 `_check/mobileprobe.js`（视口 390×844 + 触摸模拟，
**15 条断言**，不花额度），并用改前源码跑出基线。

**为什么必须新写探针**：`mapaudit` 的视口是 1440×900，那里 `matchMedia("(max-width:760px)")`
恒为 false，`tipDock()` 的整条分支**一次都不会执行** —— 窄屏专属的两条路径在桌面探针里
结构性不可见。这不是"顺手补一下"能解决的，只能另起一个窄视口的探针。

### 问题 ① 顶部区占屏过大

**基线 175 px（占视口 20.8%）／摊成 3 行**。根因：`.top-in` 是 `flex-wrap:wrap`，
中间的文字列没有 `min-width:0`，于是 `h1` 与 `sub` 先各自撑成整行、`badge` 再被挤到第三行。

压法按"信息价值"排序：sub 隐藏（技术栈罗列，纯装饰）· h1 压到 14px · badge 与标题同行 ·
logo 34→26。**sticky 改 static 是实拍才发现的第二层问题** —— 压薄后的 43 px 虽然小，
但半透明浮在内容上，实拍里正好压在"① 查询条件"的城市按钮行上、把那行截断成两半；
而顶部条带的信息（地名/日期/时段）在地图卡片与结论卡里都有，手机上它的边际价值为负。

结果 **43 px（4.4%）／1 行**，360×640 下同样成立。h1 定 14px 而非 15px：15px 会折成两行
且**断在词中间**（"概/率与观赏质量"），断行难看比小一号字更伤。

### 问题 ② 提示卡按不掉 + 遮挡

基线三个症状：指针靠上时**下方被裁 23 px** · 无任何关闭路径 · 172 px 窄卡里每行都难折。

1. **遮挡** ⇒ 新增 `.tip.dock` 贴底通栏（`@media max-width:760px`）。
   JS 侧 `tipDock()`（`matchMedia`，不用 `innerWidth`：判的是"屏幕窄"而非"容器窄"）。
   **dock 时必须显式清掉 `left/top/--tipshift` 与 `below`** —— 行内样式优先级高于 CSS。
   `max-height:72%` + `overflow-y:auto` + `pointer-events:auto`（否则窄屏既滚不动也点不着）。
2. **按不掉** ⇒ 触屏没有 `mouseleave`。给三条关闭路径：卡片 × 按钮（`@media (hover:none)` 显示）·
   **再点一次同一处**（`MapMod.pinLL` 判重）· **点地图以外**（document 捕获监听，
   **事件时**才判 `tipDock()`，init 时求值会在窗口跨断点后失配）。
3. **透明度** ⇒ `.dock` 改不透明。`.tip` 的 `rgba(255,255,255,.98)` 是为桌面 220×172 小卡片设计的，
   而贴底通栏 326×302 底下正压着图钉与数值直标，那 2% 会让它们整片透上来。层序本身是对的
   （tip z=20 > pinlayer z=6），问题纯在 alpha。像素级复核：改后卡片内空白区非白像素 **0** 个。

顺带把"藏卡片"从 7 处散落的 `classList.remove("on")` 收口成 **`hideMapTip()`** ——
只藏卡片会留下 `pinLL` 残留（误判"再点一次"）与未取消的悬停帧（卡片又被弹回来）两个不一致状态。
另修 `.t-scroll` 缺 `min-width:0`（`overflow-x:auto` 本身不封顶，会被内容一起撑开）。

### 追加 · SDK 缩放控件压住卡片与 ×（第二批真机反馈）

第一轮修完后真机又报：**贴底卡片被腾讯地图自带的缩放（+/−）与罗盘控件压住**，

给这个用的。桌面端 `.tip` 保持 z=20 不动（跟随指针的小卡片与右下角控件几乎不重叠）。

**探针同步（15 → 17 条）**：新增两条**防御性**断言 —— ① dock 卡片 `z ≥ 1000`（防回退）；

### 再追加 · 页面横拖出空白 + 地图无法左右滑（第三批真机反馈）

第二轮修完后真机又报两个症状：**① 手机无法左右滑动地图；② 整页向左滑时右侧划出
约一条空白**（截图里页面被横向拖出 ~61 px，左侧内容被截断）。两个症状同一个根因链。

**诊断（探针 F 段，先量后改）**：390 视口下实测 `body.scrollWidth = html.scrollWidth
= 451`，**唯一"直接越界"的元素是 `#topBadge`（305..451）**——其余 34 个都在
`.t-scroll` 内合法滚动。根因链：顶部标题列 `<div>` 没有 class 也就没有
`min-width:0`，flex 子项默认 `min-width:auto`，而 h1 是 `white-space:nowrap`
（其 min-content = 整行标题宽）⇒ 标题列**不许收缩**，把 `flex:0 0 auto` 的
badge 顶出容器右缘 61 px。这正是上一轮 headless 视口被放大 ×1.157 的**同一根因**
（390 设定拿到 innerWidth 451）——元素越界 → body.scrollWidth 增大 → Chrome
移动模拟把布局视口等比放大。

**为什么上一轮没抓到（自指掩盖，本轮最重要的教训）**：旧"越界"断言的参照是
`window.innerWidth`——而 innerWidth 自己就被溢出放大到 451，badge 右边界 451
**恰好等于参照值** ⇒ 断言永远抓不到自己制造的溢出。参照必须换成
`document.documentElement.clientWidth`（布局视口，不被溢出放大）。

**"地图无法左右滑"的机制**：页面存在横向溢出时，浏览器的横向平移手势会跟地图
拖动竞争（真机横滑被浏览器拿去平移页面）；且 `#map` 的 `touch-action` 是 `auto`。
`touch-action:none` 把 #map 内全部手势判定交给腾讯地图 SDK —— **只能设在 #map，
绝不能设在 `.mapwrap`**（`.tip.dock` 是它的后代且要纵向滚动，手势判定取触摸链上
所有元素 touch-action 的交集，祖先 none 会连卡片内滚动一起禁掉）。

**落地**：
① 顶部标题列加 `class="top-tx"`，`.top-tx{min-width:0}`（**只写 min-width:0，
不要写 flex:1** —— 那会跟 `.spacer` 分剩余空间，badge 不再贴右）；
代价是窄屏标题被 h1 的 ellipsis 截成「霞光预报 · 朝霞 / 晚霞 概…」——
badge（地名/日期/时段）是真正被反复看的那一行，这个取舍是值得的；
② `#map{touch-action:none}`；
③ 探针同步（17 → **21 条**）：F 段补 4 条断言（`html.scrollWidth ≤ doc.clientWidth+1`
/ `body.scrollWidth` 同 / `#map touch-action=none` / `.mapwrap` 不被设 none），
并把旧"越界"断言的参照从 `innerWidth` 换成 `clientWidth`。

**回归**：`mobileprobe` **21/21 PASS**——`innerWidth` 回到 **390**（自指解除）、
`body/html.scrollWidth=390`、越界 0、`#map touch-action=none`。
全量 `all.py` 11/11 PASS。产物 449,787 → **451,183 字节**。

### 三追加 · "部分时候"无法滑动地图（第四批真机反馈）

第三批修完溢出与 `touch-action` 后，真机又报：**部分时候无法滑动地图**。

**机制（这次能推出为什么是"部分时候"）**：`.tip.dock` 是 326×302 的通栏
（`pointer-events:auto`，卡片要能滚能点），而窄屏地图只有 420 px 高 ——
**卡片开着时，下半区起手的一切触摸都被卡片吃掉**（滚卡片/无效），上半区才能拖图。
"部分时候" = 卡片开着的时候。这不是回归，是 bottom sheet 模式的固有冲突，
此前没有给"边拖地图边收卡"的出口。

**落地（bottom sheet 惯例：Google Maps 点出地点卡后一拖地图卡片就走）**：
`_p6.js` 在 document 捕获层加 touchstart/touchmove 监听 —— 卡片开着时在**卡片外**
起手、`touchmove` 位移 >12 px 即 `hideMapTip()`。四个要点：
① **用 touchmove 位移判定而非 pointerdown**：pointerdown 时无法区分点击与拖动，
   在那里收卡会破坏"再点一次同一处收起"（pointerdown 先藏卡，click 到来时
   `pinLL` 已清空，同一处会重新弹卡）；
② 阈值 12 px：以下是点击/抖动，不收 —— 既有关闭路径一条不动；
③ 起手在卡片内不收：那是滚卡片，是卡片自己的事；
④ `passive + capture`、绝不 `preventDefault`：只读不拦截，地图手势仍由
   SDK 全权处理（`#map` 的 `touch-action:none` 保证 move 流完整）。
至此卡片共**四条**关闭路径：× / 再点同一处 / 点地图以外 / 拖动地图。

**探针同步（21 → 23 条）**：合成 `TouchEvent` 直击 document 捕获监听 ——
拖动（位移 100 px）收卡、小位移（12 px）不收；无 `Touch` 构造器的环境自动跳过。

**回归**：`mobileprobe` **23/23 PASS**。产物 451,183 → **453,414 字节**。

### 四追加 · "关闭卡片后地图滑不动 + 双指触发整页缩放"（第五批真机反馈，根因终于找到）

第四批用"拖动收卡"缓解之后，真机给出了**完整复现链**：点地点弹出卡片 → 关闭卡片 →
**地图再也滑不动**（上下左右都不行）；这时**双指缩放有概率触发浏览器整页缩放**
（不是地图缩放）；点一下页面其他地方"好像恢复"，但单指平移始终不行。

**根因（此前两轮都误判了）**：`.tip` 基础态是 `pointer-events:none` + `opacity:0`，
但窄屏媒体查询里的 **`.tip.dock` 带 `pointer-events:auto`**（卡片要能滚能点）
**+ `z-index:2000`**，而 `showMapTip` 加上 `dock` 之后，**没有任何地方移除它** ——
`hideMapTip()` 只 `remove("on")`。于是**点开过一次卡片、再关掉之后，一块
326×302 的隐形热区永久扣在地图下半部**：

- 单指落在它上面 → 触摸被这块透明层吃掉 → **地图拖不动**（上下左右都不行）；
- 双指落在它上面 → 它的 `touch-action` 是 `auto` → **浏览器整页 pinch-zoom**；
  而落在真地图上时 `#map` 的 `none` 生效 → 所以表现为"**有概率**"整页缩放。

这同时解释了为什么是"部分时候"：**没点开过卡片之前一切正常**，点开并关闭之后就
永久进入这个状态。上一轮把它误判成"卡片开着时挡住屏幕"，加"拖动收卡"只缓解了
"开着时"那一半 —— **卡片关了它还在挡**。

**落地**：
① `hideMapTip()` 里**摘掉 `.dock`**（状态收口，与它已经收口的 `pinLL`/`cancelHover`
   同一纪律）—— 关闭后卡片回到基础态 `pointer-events:none`，热区消失；
② `.tip.dock` 加 **`touch-action:pan-y`**：卡片可见时双指落在卡片上也不缩放整页
   （pan-y 放行它需要的纵向滚动，禁掉 pinch-zoom）。

**探针同步（23 → 26 条）**，其中最关键的一条是**端到端**的：记下卡片打开时的
中心点，关闭后 `document.elementFromPoint` 必须**落回 `#map` 之内**（实测命中
`canvas`），而不是命中那块隐形的 `#tip`。另两条：关闭后 `pointer-events === "none"`、
卡片可见时 `touch-action === "pan-y"`。
（探针实现踩坑一处：`elementFromPoint` 吃视口坐标，地图卡在视口外时直接返 `null`
→ 判据会误报，必须先把地图 `scrollIntoView` 再取坐标；断言同时加了
`probeInViewport` 守卫，免得判据失效时静默变绿。）

**回归**：`mobileprobe` **26/26 PASS**。产物 453,414 → **455,026 字节**。

### 六追加 · 地图：已有缓存时自动加载（B14）

**诉求**：地图数据不必每次开页都手点「加载周边地图」——**已经有缓存就该直接画出来**。

**为什么这不是推翻额度纪律**：硬约束 9「首屏不自动取地图数据」的本意是**别让取数随
页面打开自动发生**（首屏 520 个加权调用里地图占 456 个，等于把全站每天的开页次数
砍到二十次）。而**缓存命中根本不发请求** —— 这正是本地化那一系列缓存设计的既定收益。
所以放宽的边界恰好落在"发不发请求"这条线上：**有缓存就画，没缓存绝不取**。

**实现（把纪律做成一行代码，而不是两处条件互相对齐）**：
1. `loadMapData(force, cacheOnly)` 加第二参数。`cacheOnly` 的 `return false`
   放在**两条缓存快路径之后、任何网络调用之前** —— 于是"自动加载不会烧额度"
   由**那一行**硬保证。若像常见写法那样在调用方复制一份命中条件去对齐，
   镜像条件迟早会漂移（那正是约束 9 最怕的事）。
2. 新增 `autoLoadMapFromCache()`：`loadMapData(false, true)`，没画出来才显示待加载引导。
3. 挂点两处：**initMap 末尾**（首屏）与 **`mapOnPlaceChanged` 的作废分支**（换地点）。
   **不能挂在 `setLocation` 里**：小幅移动（≤ `MAP_KEEP_KM`）时地图并未失效，
   在那里尝试自动加载、又恰好没缓存，会把一张好图换成"待加载引导" ——
   localgrid 的「小幅移动不弹待加载引导」断言当场抓住了这个回归（这是本次唯一一次踩坑）。
4. `#autoMap` 文案同步改为「已有缓存直接用，无缓存才额外取数」——
   它原本写"每次都会额外取数"，在缓存自动加载之后已经**不诚实**了。

**探针（localgrid 新增 6 条）**：用 `Fetch` 拦截统计"坐标数 ≥50 的批量请求"（地图取数
的唯一可靠特征：地图 57 个坐标 / 单点 1 个 / 趋势 34 个），做**两次加载对照** ——
无缓存首屏（引导显示 + 0 批量请求 + 无数据）、有缓存首屏（自动画出 3 条带 + 0 批量
请求）。另有一条**判据自检**：显式取数必须被计数（否则"零请求"断言会因计数失效
而静默通过）。

**回归**：`localgrid` 全绿；全量 `all.py` 11/11 PASS。产物 455,026 → **457,737 字节**。

### A1 · `docfacts`：让文档漂移由机器抓

**病灶**：项目里散落着大量"可机读的事实值" —— 源码行数、产物字节、源码常量、探针断言条数 ——
它们被手抄进 README / 阶段性总结，然后随代码改动漂移，而**没有任何断言守着**。已实际发生过两次：
① `assemble.py` 的输出被重定向到 `/dev/null`，文档里记下的是**中间态**字节数；
② 手机端四批改完之后 `_p6.js` 长了 83 行，文档里的行数表没人回头改。
这类事故的特点是**静默** —— 不影响运行，只让文档慢慢变成谎话。

**三条纪律**（每条都是踩过的坑的直接对策）：
1. **只校验可机读的事实**。判"这句注释讲得对不对"是人的事，不进表。
2. **失配必须响**：某条声明在文档里**找不到**时，报 `STALE（未找到声明）`，**不能静默通过**。
   判据本身失效时的绿灯是骗人的 —— 与 `mobileprobe` 里那个 `probeInViewport` 守卫同思路。
3. **只断「等于」**。范围与约数进排除清单（额度 ≈65/171/129/236、栅格 217×200、
   缓存 56.8 KB / 754,398 字符、纱覆盖 21.6%、各探针耗时…）：它们**没有**可机读的事实源，
   写进去只会变成第二份手工维护的数字 —— 而且会逼人去改文档凑数。

**事实源三路**：文件系统（行数 / 字节）· 源码正则（`const` 常量，支持 `A = B` 别名回溯）·
`_check/.facts.json`（各探针末尾那行 `FACTS {...}`，由 `all.py` 连同**探针源码 sha1**
一起写入，支持增量合并，`-k` 单跑只刷新被跑到的条目）。

**"不拿旧数字冒充真相"**：`docfacts` 比对 sha1，源码改了而事实行没重跑 ⇒ 报 STALE 并提示重跑，
而不是沿用上一次的数字。

**收口时它自己报了 6 处**（源码行数 3 处 / 产物字节 / 序列项数）—— 全部按实际值改完。
声明条数 31 → **33**（新增 `persistprobe` / `a11yprobe` 的断言条数）。
**这是本轮最省心的一个成果：漂移不再靠人回头翻。**

### A3 · 绘制性能基线（只测量，不判成败）

`_check/perfprobe.js`：3 场景 × 3 节流档（1× / 4× / 6×）× 9 次采样，报中位数与最大值，

实测（中位数）：复绘 **10 / 63.3 / 95.8 ms**；首次（重建值场）**21.5 / 84.5 / 145.2 ms**；
全图层 **18.4 / 94.8 / 180.7 ms**。按方案原定"没超预算就不优化"⇒ **未发现需要优化的证据**，
一行业务代码都没改。

**踩到的坑（值得记）**：CDP 的 `Emulation.setCPUThrottlingRate` 注入在**任务调度**上，

### B2 · 趋势结果缓存

**账**：趋势窗口一次约 129 次加权调用，占单页全量 **55%**（129/236）；而它算完的结果
只是一张 10 行的表。

**存什么（本轮的关键决定）**：存**算好的 rows**，**不存原始响应**。原始响应约 5 MB
⇒ 撑爆 5 MB 配额 ⇒ **所有**缓存静默失效；rows 实测 **1,863 字符**。代价是
"权重 / 阈值一变旧缓存就错"，用 `TREND_CACHE_PREFIX` 版本号兜住。

**与 B14 同构的一行硬约束**：`loadTrend(cacheOnly)` 的 `if (cacheOnly) return false;`
放在两条缓存快路径**之后**、任何网络调用**之前** —— "自动加载不烧额度"由**那一行**保证，
而不是靠调用方复制一份命中条件去对齐（镜像条件迟早漂移）。

**实测**：无缓存开页 0 批量请求 + 不打扰用户；有缓存开页 **0 请求 / 20 个格子**自动画出；
换地点后旧趋势作废。**另附一条容易记错的差异**：三个缓存键族共用 `mapCacheSweep` 总闸门，
但"豁免当前地点"恰好**相反** —— 地图 `true`（另有按日期 LRU 兜底）/ 单点 `false`
（无其他淘汰机制，豁免会撑爆配额）/ 趋势 `false`。

### C2 · 回归耗时（cdp 分段计时 + `--fast`）

**先把时间拆开看，再决定跳哪一段**：给 `cdp.js` 加段落计时。第一张表就抓到
**125.8 s 的静默空等**（占全段 59%）—— 首屏就绪判据还是"`#rank` 有行"，而 B11 之后首屏
**根本不取地图数据**，条件永远不成立 ⇒ 每次都把 80 轮 × 1.5 s 的预算跑满，且**不报任何错**。
改成"单点结果已渲染"（`State.result.P != null`），并加一条断言防复发
（"首屏就绪等待没有跑满预算"）。

第二项大开销是 **两处固定 `await 20 s`**（等城市搜索触发的预报落定）：mock 下响应是即时的，
这 40 s 纯属浪费。改成"等 busy 起来 → 等 idle"两段轮询（上限不变），与文件里既有的
`waitIdle` 同一纪律。

**`mark(name)` 的语义修正**：原来的 `tick(n)` 是"给**接下来**那段命名"，读代码得数位置对齐；
实际就错位过一次（十一个标签整体位移一位、表里两行同名）。改成"给**刚结束**的那段命名"，
调用点上面的代码就是它的名字，不可能错位。

**`--fast`**：不再是"把 cdp 整段删掉"（那会把端到端覆盖一并删掉，而端到端正是 cdp 存在的
理由），改成 `CDP_SEG=fast` —— 照常起浏览器、照常跑完前中段全部断言，只跳过两段
（算法模型切换 —— 与 S5 的 48 组合遍历重叠；B5 并发点击 —— 另有 `raceprobe` 覆盖），
且**各打一行「已跳过」**，不静默略过。

**实测：cdp 215 s → 57 s（普通）/ 51 s（`--fast`）**，FAIL 计数 0。要如实说明的是：
省下的时间**绝大部分来自"去掉固定等待"而不是跳过** —— 那次空等 125.8 s、两处固定 20 s 约
40 s，而 `--fast` 的两段跳过只再贡献约 **6 s**（因为那两处 20 s 本来就落在被跳过的段里，
改轮询之后那段的实测耗时已经从 31.6 s 掉到 7 s）。

## 第八轮追加 · 产物改名为 `index.html`（并收口散落的"产物名"）

**诉求**：让同一份自包含产物**既是本地可双击的文件、又是静态托管的站点入口** —— 静态托管
（GitHub Pages / Cloudflare Pages / 对象存储）都按目录里的**默认文档名**取首页，`index.html`
是通用约定；顺带避开中文文件名在托管 / CDN 上的 URL 编码（`%E9%9C%9E…`）与大小写不一致问题。

**核心纪律：改名 = 只改文件名，一个字节都不动。** 证据是哈希而不是肉眼：
`sha256 930f1311…` 在改名前后**完全一致**，改完构建脚本后重跑 `python assemble.py`，
产物仍是 **472,141 字节 + 同一哈希** ⇒ 内容与自包含性（内联 JS / 城市表 / 0.5° 高程网格 /
data-URI 图标）都没受影响。同时确认产物里**没有相对引用**：全文只有 data-URI 图标与一个
绝对地址的外部脚本（`map.qq.com/api/gljs`），所以换文件名打断不了任何引用
（对自包含产物来说"相对引用不受影响"是可以被验证的，而不是只能靠承诺）。

**代价（本轮的教训）**：产物名在项目里**散落 9 处**，只 `mv` 一个文件会让管线**静默半死** ——
`python mkpreview.py` 与 `syntax` / `run_self` / `datacheck` / `timeoutprobe` 会**直接
`FileNotFoundError`**（实测四例），`docfacts` 的 `product.bytes` 变成"事实缺失"。
改名必须同步：

| 位置 | 说明 |
| --- | --- |
| `assemble.py` | `OUT` 与末尾 `wr()` —— 产物名**只在这一处定义**，其余全是"读" |
| `mkpreview.py` | 读产物生成 `_check/preview.html`（**联调页是全部探针的输入**，它挂则整套回归跑不起来） |
| `_check/syntax.py` · `run_self.py` | 读产物、抽出 3 个内联 `<script>` 块做语法 / 纯函数自测 |
| `_check/datacheck.py` | `PRODUCT` 常量 |
| `_check/docfacts.py` | `PRODUCT` 常量（`product.bytes` 的事实源） |
| `_check/timeoutprobe.js` | 读产物注入超时 / 429 用例 |
| `_check/aodscale.js` | 读产物（不在主序列） |
