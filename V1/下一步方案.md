## 0. 先给结论：重心该换了

前几批一直在抠**额度**。但把账算清楚之后，额度已经不是瓶颈：

| 口径 | 加权调用 | 免费层 10,000/天可支撑 |
| --- | --- | --- |
| 首屏（只看单点结论） | **65** | ≈ **154 次/天** |
| 单页「全量」（单点 + 点开地图） | **236** | ≈ **42 次/天** |

对一个个人使用的预报页，42 次/天够了。**继续抠额度的边际价值已经很低。**

而这次为了写方案做的一次实测，发现了一个**用户能直接看见的矛盾**：
同一地点、同一天、同一时段，上面的结论卡和地图中心的数值对不上（实测差 2.0 分）。

所以下一批的重心应该是：

> **口径一致性（让两个入口对同一件事说同一个数）+ 可信度表达（把"这个数有多可信"从附注提到台面）**
> —— 而不是继续省额度。

## 1. 已核实的三件事

### 1.1 单点与地图中心口径不一致 ★ 实测

**两个入口用的是两套样带：**

| | 样带 | 点数 | 数据来源 |
| --- | --- | --- | --- |
| 结论卡（`computeAll`） | `TRANSECT` = 0, 25, 50 … 400 km | **17** | 全部**真实取数** |
| 地图每个网格点（`loadMapData`） | `d = 0` + `d = MAP_AZ_KM(250)` | **2** | 只有 d=0 是真实值，d=250 由 57 点云场 IDW 插值 |

**实测（真实接口，`_check/consistency.js`，广州 2026-10-09 晚霞）：**

```
地点        : 广州市  (23.1291, 113.2644)
单点  P/Q/I : 25.6 / 27.8 / 26.6
地图  P/Q/I : 22.8 / 26.8 / 24.6      (网格中心点，距查询点 0 km)
差值  ΔP/ΔQ/ΔI : -2.8 / -1.0 / -2.0
```

差值不大，但**确实存在**，而且根因是结构性的：`analyseTransect` 在 2 点样带上
只能分辨"0 km 处有没有云 / 250 km 处有没有云"，云边界距离的粒度被压成两档；
17 点样带能看出 100–300 km 之间的云层分布。天气形势一旦让几何项（`W_STAT.geom = 0.16`）
占主导，这个差会显著放大。

**修法（零取数）**：把地图的 `trOf()` 从 2 点加密到 **3–5 点**（中间点同样走 `idwSample`，
不产生任何新请求），并把外点距离从 `MAP_AZ_KM = 250` 对齐到单点样带的量级。

**代价与纪律**：
- 地图数值会变 → `MAP_CACHE_PREFIX` **必须从 v4 升到 v5**（这是硬约束 1 的适用场景）。
- `zoomprobe.js` 的 136 项像素断言要按「有意的语义变更」重做双重差分（不能拿改造前的实现当基准）。
- 加密后地图成本**不变**（仍是 171，IDW 不取数），但 `geomSig` 只编点集坐标，
  样带改变不影响它；影响的是**值场数值**，所以缓存版本必须升。

### 1.2 单点请求里 `dew_point_2m` 是冗余变量

`buildEnv`（`_p4.js:268`）本来就有兜底：

```js
if (isNum(env.T) && !isNum(env.Td)) {
  env.Td = env.T - (100 - clamp(nz(env.RH, 60), 1, 100)) / 5;
  missing.push("dew_point_2m");
}
```

而地图侧 `F_MAP_VARS` 就是靠这条把变量压到 9 个的（注释里写得很明白：
"露点可由温度+相对湿度反推"）。**单点侧却仍然请求了 `dew_point_2m`。**

删掉它：`F_VARS` 14 → 13，权重 `max(1, 14/10)=1.4` → `max(1, 13/10)=1.3`，
**每页省 2×17×0.1 = 3.4 个加权调用**（236 → 232.6）。
**零精度损失** —— 走的正是同一条兜底路径，只是把"接口给的值"换成"自己算的值"。

> 收益很小，但它同时是一次**清理**：请求了 14 个变量，其中 1 个从没被真正需要过。

### 1.3 多模型合并成一次请求：技术上可行，**但不建议做**

实测（HTTP 200）：

```
/v1/forecast?…&hourly=cloud_cover_low&models=gfs_seamless,ecmwf_ifs025
→ hourly 里出现 cloud_cover_low_gfs_seamless / cloud_cover_low_ecmwf_ifs025
```

一个坐标一次请求就能拿到两套模式 —— 请求数可以从 3 降到 2。**但不要这么做**：

- 合并后变量数从 9 变成 18，**跨过「超过 10 个变量」这条计费阶梯**，
  单坐标权重从 `1.0` 跳到 `1.8`。而"模型数是否另行相乘"官方文档没有明说。
- 收益不确定（可能省、可能反而更贵），风险确定（变量数翻倍）。
- 请求数少 1 只省几百毫秒，不值得为它承担计费不确定性。

## 2. 计费式已核实（把账目钉死）

> **加权调用 = `max(1, 变量数/10) × max(1, 天数/14) × 坐标数`**

四个实测点全部对上：

| 请求 | 变量 | 天数 | 坐标 | 计算 |
| --- | --- | --- | --- | --- |
| 单点 forecast ×2 | 14 | 3 | 17 | `1.4 × 1.0 × 17 = 23.8` 每个 |
| 单点 AQ | 4 | 3 | 17 | `1.0 × 1.0 × 17 = 17` |
| 地图 forecast ×2 | 9 | 1 | 57 | `1.0 × 1.0 × 57 = 57` 每个 |
| 地图 AQ | 4 | 1 | 57 | `1.0 × 1.0 × 57 = 57` |
| **合计** | | | | `47.6 + 17 + 114 + 57 = 235.6` ≈ **236** ✓ |

官方 FAQ 的两个示例也吻合：15 变量 × 2 周 = `1.5 × 1.0 = 1.5` ✓；
15 变量 × 4 周 = `1.5 × 2.0 = 3.0` ✓。

**推论**：单点与地图的**时间跨度系数都已经踩在下限 1.0**（3 天和 1 天都远小于 14 天），
所以"缩短时间窗"省不到任何额度；**唯一有效的额度杠杆是变量数**。

## 4. 批次 B · 零取数的新能力（3 项）

### B1 分享卡导出（把结果变成一张图）
使用场景就是"今晚要不要去看晚霞" —— 用户要的是**能发给同行人的一张图**，
而现在只有 URL。做法：**纯 canvas 手绘**（不引外部库，保持单文件），
数据全部来自 `State.result`，`toDataURL()` + `<a download>` 落地。
卡片内容：地点/日期/时段 + 概率环 + 分数与等级 + 一句结论 + 三个模式的小字。
**零取数**，离线可用。

### B2 把「可信度」提到台面
现在 `consist`（`_p4.js:427`，`100 − 极差×1.9`）、`spread`、地图的 `dv` 维度
**都已经算好了，只是散落在附注和地图维度里**。合成一个总览徽标放到结论卡顶部：
「模式一致性 高/中/低」+ 一句话解释（哪两个模式分歧最大、分歧在概率还是在质量）。
**零取数** —— 数据早就在结果对象里。

### B3 单点侧也显示三模型分歧
地图有 `dv`（模型分歧）维度，单点只有"GFS 与 EC 的分歧"一句附注，
**光追那一路没进分歧口径**。而 `parts` 里三套结果本来都在。
把单点分歧口径与地图 `dv` 统一（`max(I) − min(I)`），**零取数**。
