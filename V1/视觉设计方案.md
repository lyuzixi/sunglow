> 状态：**待评审**。评审通过后才进构建；本文所有成本估算都经过源码核实，不是估计。

## 一、题材与判断

**这是什么**：预测朝霞 / 晚霞（火烧云）出现概率与观赏质量的单文件应用。用户是“今晚要不要上天台、明早要不要出门”的人和追霞光的人。它的**唯一职责**：先一秒回答“有没有、好不好、何时、往哪看”，再给愿意深挖的人完整的物理与模型依据。

**设计判断**：这个应用的题材本身就是一种视觉现象——**曙暮光**。界面不该“装饰”霞光，而应该**把天色本身变成信息**。当前界面把唯一的主题资产（白→黄→橙→红的霞光色阶）关在地图图例里，页面骨架却说着中性的“后台管理”语言。本方案要做的是：让页面骨架也呼吸天色，但守住一条纪律——**完整的霞光色阶只属于地图数据，页面本身只讲“纸墨 + 一笔暖色”**。

**一个 memorable 的东西**（skill：boldness 花在一处）：把结论卡的头部换成一条**天色带**——按当日当地真实太阳高度角分段着色的曙暮光序列，霞光窗口直接标在带上。它既是装饰也不是装饰：它就是这个应用所预报的那个现象本身。

## 三、Token 系统

### 3.1 颜色（浅色；深色只换令牌值，不换结构）

| 令牌 | 值 | 角色 |
|---|---|---|
| `--paper` | `#f4f5f7`（≈现 `--bg`） | 页面纸面，冷中性 |
| `--card` | `#ffffff` | 仪器面板面 |
| `--ink` | `#1c2330`（≈现 `--tx`，暮色蓝黑） | 主文字 |
| `--ink2` `--ink3` | `#5b6675` `#667081`（**不动**，已审计） | 次/弱文字 |
| `--glow` | `#e2601f`（霞光橙，不动） | 唯一暖色，**只给数据** |
| `--glow-ink` | `#bd4a17`（不动，已审计） | 暖色文字安全值 |
| `--dusk-*`（新增 5 个） | 见下 | **只属于天色带**的固定曙暮光序列 |

**天色带专用序列 `--dusk-*`**（按太阳高度角分段的物理序列，固定值、不随数据拉伸——与地图色阶的“当日拉伸”刻意区分，两套色阶永不混用）：

| 段 | 太阳高度 | 色值 |
|---|---|---|
| `--dusk-day` | > 0° | `#dde5ee` 白昼余晖 |
| `--dusk-civil` | 0 ~ −6° 民用曙暮光 | `#f0c48c` |
| `--dusk-nautical` | −6 ~ −12° 航海曙暮光 | `#d9784a` |
| `--dusk-astro` | −12 ~ −18° 天文曙暮光 | `#7a759f` |
| `--dusk-night` | < −18° | `#2b3450` |

纪律：这 5 个值**只出现在天色带里**；页面 chrome、徽章、按钮一概不许引用。深色模式下天色带保持同一序列（它本来就是“天”，不需要反色），只把 `--dusk-day` 压暗一档。

### 3.2 字体（单文件约束 ⇒ 只用系统栈，零外部字体文件）

**两个角色，界限分明**：

| 角色 | 栈 | 用在哪 |
|---|---|---|
| **声音（衬线）** | `"Songti SC","STSong","SimSun","Noto Serif CJK SC","Source Han Serif SC",serif` | hero 结论句（21px/600）、各卡标题（15px/600）、hero 大数字（44px/800） |
| **仪器（无衬线）** | 现有系统栈（不动） | 控件、正文、标签、表格、图例 |

- **等宽体收缩防线**：只留给真正对齐成列的数字——趋势表 / 对比表的数值格、方位距离读数。`.kv` 的值改无衬线 600（D4）。
- 字阶（沿用第五轮收敛后的 12px 辅助档）：12 辅助 → 13 正文 → 13.5 控件 → 15 卡题（衬线）→ 17.5 顶栏题 → 19 副数字 → 21 结论句（衬线）→ 44 hero 数字（衬线）。
- **风险已知**：Windows 上 SimSun 在 ≤12px 有 bitmap 提示发虚——所以衬线只用于 ≥15px 处，小字一律无衬线。cdp 截图跑在 Windows Chrome 上，第一轮构建后必须看实拍确认。

### 3.3 天色带（hero 的核心组件）

```
 日落前1h ──────────────────────────────── 日落后1.5h
 ├─白昼余晖─┬──民用曙暮光──┬─航海─┬─天文─┬─夜─┤
 │          │   ▓▓▓▓▓▓    │     │     │   │   ← 底色 = solarPosition() 实时算出的
 │          │  ▲霞光窗口   │     │     │   │     太阳高度角分段（固定序列，非装饰）
 │          │  1分46秒     │     │     │   │
 └─ 18:23 ─┴─ 19:23 日落 ─┴─────┴─────┴─┘
```

- 分界不是画的，是**算的**：`_p2.js` 的 `solarPosition(ms, lat, lon)` 现成返回高度角，0/−6/−12/−18° 四个边界直接求（零新算法）。
- 霞光窗口：以事件时刻为锚、按 `geom.dur` 展开的段，段上标持续时间（锚点的精确语义在构建时对照 `fireGeometry` 核实——已在成本里列为待办）。
- 轴下刻度只标三个真时刻：窗口起点、日落/日出、民用曙暮光结束（“天开始真正黑”）。
- P2 叠加层：逐时云量（计算层 `serG/serE` 序列已在内存，只需在结果对象里留一个切片，**零新增请求**）画成带上的淡纹——云会不会挡，一眼看见。

### 3.4 原则（五条）

1. **色阶只属于霞光**：完整白→黄→橙→红只出现在地图/图例；页面讲纸墨与一笔暖。
2. **应用只开口说一次话**：结论句是全文唯一的散文——它独享衬线声音；其余一切是仪器。
3. **hero 展示天色，不只展示数字**：最 characteristic 的东西是第一屏。
4. **编号取消，层级交给排版**：不编号、不加眉标；主次靠字重、衬线/无衬线、阴影的有无。
5. **一次编排动效，其余安静**：首次预报完成时天色带的霞光窗口与数字轻扫一次（≤600ms）；`prefers-reduced-motion` 时全静。按钮/展开等“回答动作”的过渡保留。

### 实现中抓到的三个真问题（如实记）

1. **霞光窗口的方位语义不能"以事件为中心"**：`fireGeometry` 的 `dur` 是太阳从
   云边界遮挡角 θnear 走到地球遮挡角 θfar 的时间 —— 晚霞窗口整体在日落**之后**、
   朝霞整体在日出**之前**。计划里的"以事件为锚展开"是错的，已按真语义实现；
   uiprobe 用**纯函数判据**死守这条（构造已知几何直接调 `skyBand()`，不依赖当天数据：
   晚霞 win.left 16.6% > 事件 13.0%，朝霞 win 79.8–83.4% < 事件 87.0%）。
2. **窗口符号**：`thNear/thFar` 是**俯角**（正数），窗口对应的高度角是**负**的。
   第一版把正值传给二分 ⇒ 穿越不存在 ⇒ 窗口恒为 null（实拍里那条橙线根本不出现）。
   修法：`cross(-θnear)` / `cross(-θfar)`。**这条只有看实拍才能发现** —— uiprobe
   当时的合成数据恰好几何不成立，条件断言被跳过；后来补的纯函数判据才把这条锁死。
3. **橙线压橙底**：窗口落在中国曙暮光段（tan 色）上，橙色底线几乎不可见；
   加 1px 白色上沿做分离，并给 `min-width:3px`（1分46秒在带上只占 1.8%）。

### 探针侧的另一条教训

## 十一、视觉方案四 · 纸面仪器（当前）

四问全取推荐项：**纸面仪器**（冷白纸面、发丝细线分区、衬线只给数字与结论句）/
**结构与文案都可动**（同步改探针）/ **答案优先**（天色带顶到第一眼）/ **浅色为主，
深色同等打磨**。

要解决的是前三轮留下的同一个病：视觉语言是"通用 SaaS 卡片套装"——奶油底、
圆角+阴影一律、卡片标题都挂一枚同款副标题、强调色到处发光。这套东西不缺
"好看"，缺的是**判断**：所有元素同等重要，等于没有层级。

### 三条纪律

1. **纸面是冷中性的。** `--bg:#f6f7f8`（不是奶油 `#faf7f2`）。暖色只给数据本身
   ——色面、等级、日轮；界面装饰一律灰阶。避免"AI 默认配色"的第一眼。
2. **层级靠排版与发丝线，不靠阴影。** 正文阴影收到 `0 1px 2px rgba(16,24,40,.03)`，
   四个渐变令牌（`--grad1/--grad2/--grad1t/--grad2t`）**整套删除**：body 光晕、
   综合模型卡的渐变底、按钮渐变全部消失。
3. **对比度是审计过的，不是调出来的。** `--tx3` 与 `--acc2` 的明度一律不动
   （a11yprobe 守 4.5:1），只重排层级顺序，不动可读性下限。

1. **深色 `--solid` 不能近白。** 最初给成 `#e9ecf1`，深色页上墨色按钮炸出一块

2. **轴标签按身份数，不按总数。** `renderHero` 在"当前时刻落在带内且离事件 >8%"
   时才多画一枚 `.nowlbl`，所以轴上 `<span>` 数会在 2 / 3 之间随跑批钟点变化。

3. **删令牌要连带清掉使用点。** `--grad1` 删掉后，404 页 `body` 仍写着

   修法不是改阈值，而是把判据的**语义**改对：单选组≠记录器。

## 12.1 轴上的时间：现在 / 太阳事件 分两行（同日修正）

用户拿截图来问"优化这里的时间显示"，图上 `天黑 19:15` 与 `现在 19:18` 叠成
一句「天黑 1现在 19:18」。这不是错位，是**两枚标签在同一行抢同一条像素带**。

### 根因（先量再说）

原实现三枚标签都在 `.skyaxis` 这一行里绝对定位：事件左锚、天黑右锚、现在居中，
避让条件只写了 `Math.abs(nowPct - evPct) > 8` ——**只避「日落」，没避「天黑」**。
而「现在」只在天黑前后那一小时内出现在带内，正是最常被看到的时段。

实测（1440×900，`.sky` 宽 1190px）：

| 元素 | 位置 | 说明 |
|---|---|---|
| `.sky` | x 125 → 1315 | 出血到卡片边 |
| `日落 18:00` | x 279.7，宽 52.7 | 左锚于 evPct |
| `天黑 19:15` | x 1154.1 → 1207.5 | 右锚于 darkPct＝**90.9%** |
| 带右缘 | 1315 | 天黑之后还有约 9% 的夜间段 |

两个发现：
1. **「天黑」并不在轴的右端**（90.9%），后面还有夜间段。所以凡是"现在已过天黑"
   的时刻，都落在天黑标签**右侧一点点**——居中标签的半宽正好压上去。
2. 旧代码用 `clamp(nowPct, 6, 94)` 防出界，结果标签被拽离自己的刻度线（刻度在
   97%、标签在 94%），既撞车又脱钩。

### 做法

- **两行制**：上行只放这一天自己的两个真时刻（事件左锚 / 天黑右锚，永不移动），
  下行放「现在」游标。二者**物理上不同行**，重叠不可能发生。
- **锚点随位置切换**：`nowPct ≥ 88` 右锚（`translateX(-100%)`）、`≤ 12` 左锚、
  中段居中。三种情形下标签都贴住刻度线，且都不越出面板。`clamp(…, 6, 94)`
  这套"把标签挪开"的写法删除。
- **高度按需**：`.skyaxis.two{height:32px}`（移动端 30px），没有「现在」时仍是
  一行 16px —— 不是当天的日期不多占一行空白。
- **相对量只进 `title`**：`天黑已 3 分钟` / `距天黑 6 分钟`（两枚新词条，三语）。
  轴的正文保持三个绝对时刻，窄屏不会因为一句关系从句被拉长。
- 字号/行高显式声明（11.5px/16px，移动 11px/15px）：两行间距 16px 是算出来的，
  不靠浏览器默认行高，否则 11.5px 的默认 line-height 会让两行文字互相咬住。

### 判据（这条最重要）

**不能等真实钟点撞上再判**——那正是这类 bug 的形态：一天里只有傍晚一小时会红。
A3 的做法是**克隆**真实轴节点，把它摆到 0 / 50 / 100% 三个极端位置，实测三件事：

| 判据 | 阈值 |
|---|---|
| 在框内（不越出面板） | `left ≥ axis.left - 0.5 && right ≤ axis.right + 0.5` |
| 贴住刻度线 | 刻度 x 落在 `[label.left - 1.5, label.right + 1.5]` |
| 与两枚事件标签不相交 | 矩形交集为空，且行距 ≥ 10px（实测 16px） |

克隆测的是 **CSS 合约**，与跑批钟点无关，因此不会忽绿忽红；同时它测的是真实节点
的文案与字体，宽度不是我猜的常量。实测输出：

```
现在@  0% · 在框内=true · 压住刻度=true · 与事件标签相交=false · 与最近事件标签的行距=16.0px
现在@ 50% · 在框内=true · 压住刻度=true · 与事件标签相交=false · 与最近事件标签的行距=16.0px
```

### 教训（第 5 条）

**同一行里放"两个会随时间靠近的东西"，早晚会撞。** 避让逻辑写得再细也只是
在推迟碰撞：判定阈值要跟着字号、语言、容器宽度变，而且永远漏一个方向（这次漏的
就是"天黑"）。正确的解法是**改结构**——把静态刻度与动态游标分层。分层之后，
判断成本是零，判据也能写成确定的几何合约。

## 12.2 轴升级为时间尺：四道分界各标「名称 + 时刻」（同日第二次修正）

用户要求"给颜色间隔处标上时间"。四道色块分界（0/−6/−12/−18°）此前只有首尾两枚
有名有时刻，中间两条是空的——民用段、航海段各持续多久，要靠心算。

### 拍板

四条全标、中间带名称：**日落 18:00 · 民用终 18:23 · 航海终 18:49 · 天黑 19:15**；
挤不下时**名称自动降级**（隐名称只留时刻 → 按间隙舍弃中间标签；首尾永不丢）。

### 实现要点

- **名称随时段转向**：晚霞是各段的「终」，朝霞是「始」；−18° 晚霞叫天黑、朝霞叫
  天亮。顺带修掉既有错标——朝霞时 −18° 那枚一直写着「天黑」。
- **排版分工**：名称安静（`--tx3`），时刻是主角（`<b>` → `--tx2/600`）——一条轴上
  四枚粗体全是钟表，扫一眼就是一条时间线。标签默认整体居中于自己的分界。
- **`fitAxis()` 实测降级**：标签宽度随语言与字号变化，估宽在英文下必失准，所以
  用 `getBoundingClientRect` 阶梯降级（越界改锚 → 隐名称 → 舍弃与邻居最贴近的
  中间标签），幂等可重入（resize 防抖重跑）。`typeof window` 守卫必须有：
  run_self 会在 Node 里裸载源文件，顶层挂 resize 监听会炸掉纯函数自测。

### 判据 A4（40 → 43 条）

① 四枚刻度齐全、时刻按时间递增、首尾保留；② **每枚标签的中心压在相邻色块的
交界上（±2px，实测 0px）**——"标错位置比不标更糟"；③ 降级阶梯端到端：把轴压窄
到 **180px** 逼出 `.tonly`（第一版用 300px 落空——这条几何的分界间距宽，300px
恰好排得开，根本没有降级可测），窄轴下无重叠，还原后完全复位。

### 教训（第 6 条）

**"敌意测试"的强度要按最坏情况校准，而不是按"看起来够窄"**。300px 听起来很窄，
但这条几何的民用/航海段各占 23%，300px 里四枚全称标签恰好排开——断言全绿，
却什么都没测到。判据落空比判据失败更危险：它会给你"守住了"的错觉。
