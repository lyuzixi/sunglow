一、诊断：地图到底"怪"在哪里

用户原话："有点怪怪的"。经决策树定位为两个症状，都指向同一族根因——色面太重、太闷、把地图盖死了。逐层挖下去，每个症状都有一条完整的证据链。

症状一 · 色面像一张"大橘饼"

根因链（三乘一）：当日值域拉伸 × 顶端档间对比度不足 × 单色相平涂 × 0.9 不透明度糊成一片
  1. 当日值域拉伸是直接根因。_p6.js:2117 把 57 个点的数值按当日值域 scaleT(v, R.lo, R.hi) 拉伸到 0–100 再切档。而当天实测中间一半格子只跨 9 分（当日值域共 77 分），且高值点占多数 ⇒ 整张色面全挤在色阶最顶端约 12% 的位置。源码注释自己写着（_p6.js:194–195）："整片色面落在一条很窄的色段里，看上去就是一坨"。
  2. 顶端那几条档本来就分不出。N_BANDS=7 的相邻档对比度只有 1.13–1.36（源码注释自述），档界读得出来靠的是等值线而不是色差。于是"一坨深橙/红 + 几条蜿蜒细线"就是全部画面。
  3. 单色相平涂没有第二个维度。HEAT_RAMP（_p4.js:545）是白→黄→橙→红的单一暖色相 8 锚点。即便值域正常，一整片同色相仍然没有空间结构可读。
  4. 0.9 的不透明度把底色糊死。色面以 0.9 盖在被压暗 0.45 的底图上，剩下的 0.1 × 0.55 约 5% 底图信息，等于没有。

附带一处"名不副实"：图例刻度写着 0 20 40 60 80 100（template.html:1397），但色条实际显示的是拉伸后的位置——刻度是绝对的、色条是相对的，读者会被系统性地误导。固定刻度后这把尺子才变成真的。

症状二 · 底图被盖住、地图感弱

根因链：色面 0.9 不透明度 × 底图 0.45 压暗 ⇒ 底图地名/海岸/道路不可辨 ⇒ 色面从"地图上的数据层"退化成的"一张热力图贴纸"

用户要的是"地图"，不是热力图。方位距离环、经纬网都在讲地理故事，但承载它们的地图本身看不见。这与"数据优先"并不矛盾——数据优先可以让颜色最饱和，但不该让地图消失。

两个"不是问题"的排除项

  • 线条乱：等值线/经纬网/方位环/范围线四套线，用户实测无感（决策树第 1 问未选）。本轮不动线元素，只把有机边缘与云纹这两个"面"的层次做出来。
  • 信息没主次：未选。说明当前"图例 + 排行榜 + 提示卡"的分工是可接受的，本轮只做配套改写（固定色阶后图例文案必须重写），不重排信息架构。

三、天色色阶（本方案的核心）

设计语义：地图上的颜色就是天空的颜色。这与视觉设计方案的核心判断一脉相承——"界面不该装饰霞光而该把天色变成信息"：差＝天色已暗（墨蓝），一般＝暮色四合的雾灰，良＝金色霞光，优＝最浓的橙红。用户已经在首屏天色带上学过这套语言（深蓝段＝天黑），地图只是把它延伸到空间维度。

工程约束（为什么可以放心换）：全应用取色只有一个源头——bandColor() → rampColor() → HEAT_RAMP（_p4.js:545–562）。色面栅格 LUT、省级色块、图例色条、排行榜条形、悬停色块全部从它取色；重定义 HEAT_RAMP 一处，全应用同步换肤。探针的取色断言（zoomprobe 136 项、mapaudit I 段）全部是自指的——期望色由页面自己的 bandColor() 算出，所以换色阶零断言改动。

  • 语义纪律的刻意扩展："暖色只给数据"扩展为"天色只给数据——地图是全天色语汇的唯一栖息地，页面纸面仍旧冷中性"。
  • 分歧（dv）维度说明：固定刻度下模型分歧（通常 <30 分）自然落在低段蓝区——这是诚实的（三模型很少强烈分歧），图例按维度给档位名，不与"优/良"混排。

四、批次计划

第一批 · 治"怪"（视觉四件套）直接回应用户两张原票

V1 · 固定 0–100 绝对刻度 改计算口径 · 不动缓存

V2 · 天色色阶换肤 改一处常量 · 全应用跟随

  • 落地时实测：a11yprobe 对比度全过；darkprobe 硬编码色预算（现 43/45）不增加——色值是数组内替换，不新增字面量。
  • 深色模式实拍复核：墨蓝低端在深色底图上的可辨性。

验收：色面/图例/排行榜/悬停色块/省级色块五处同源同色（mapaudit 既有断言）；实拍 before/after 对比。

V3 · 有机噪声边缘 改绘制 · 三对齐不破

改动：_p6.js（evalField 的凸包外羽化计算，新增确定性噪声函数）

  • 70 km 羽化的外沿叠加低频确定性噪声（网格坐标哈希值噪声，波长约 150–250 km、幅度约 ±25 km）⇒ 色面边缘像天气系统的覆盖区渐隐入地图，不再是一条几何折线。
  • 只用确定性噪声（禁 Math.random）：同一栅格永远同一边缘，探针才可复现。
  • 内边界（凸包）一动不动 ⇒ B1 范围虚线 / 可信度纱内边界 / 色面淡出内边界的三对齐（约束 19）原样成立；纱的"起纱≡外推"判据读实际像素，自动跟随。
  • 与"磨圆折角"（第三轮已判定回退）是两件事：不动顶点，只软化外沿。

验收：mapaudit J 段三对齐断言全绿；边缘目视无折角；两次构建的色面边缘逐位一致（确定性）。

V4 · 双降不透明度 改 CSS · 像素探针零影响

改动：template.html（.rlayer 基础 opacity:.75、.dimbase.on .45→.3）· _p6.js 的 FIELD_OPACITY 保持 0.9 不变

  • 关键实现决策：不把 0.75 写进画布 alpha（img[o*4+3]），而是用 CSS 层透明度实现——视觉等效，但 zoomprobe/mapaudit 读的是画布像素，所有像素级断言原样有效（否则 alpha 峰值 207→172，I 段"≥200 不透明区"会退化成空集、线宽归一标尺失效，白白削弱守卫）。
  • .rlayer.stale（opacity:.4）特异性高于 .rlayer，陈旧态不受影响；深色模式 filter 与 opacity 可叠加。
  • mapVisibleAt() 读画布 alpha>0，与 CSS 透明度无关，排行榜口径不变。

验收：底图地名/海岸在色面下可辨（实拍）；zoomprobe 136 项与 mapaudit I 段零改动全绿。

第二批 · 结构与实用（六项）含唯一一次缓存升级

S1 · 云量淡纹 动缓存 · 动图层号 · 需实测拿捏

改动：_p6.js（box.pts 加 cld 字段、buildField 增云量值场、新图层 .txlayer 绘制）· template.html（图层号重排 + z-index + 深色 filter 名单）· MAP_CACHE_PREFIX v5→v6

  • 数据侧：逐点低/中云遮挡量在管线里已算出（提示卡"主要云层"同源，_p6.js:3010–3021），但不在缓存载荷里（box.pts 只有 P/Q/type/cover/d/dur…）⇒ 每点补一个 cld（低+中云加权，0–100）并升 MAP_CACHE_PREFIX。旧版缓存缺字段 ⇒ 静默走"无纹理"路径，不报错（坏行降级是项目惯例）。
  • 绘制侧：云量按同一套 IDW 插值成场，画在独立新图层 .txlayer（z-index 2，逐纬度条带画布，与 .conflayer 同构），深云影 #1e2a44、目标 α≤0.18。绝不画进色面栅格——这是"像素色↔档位 ±2"断言（mapaudit I 段 / zoomprobe）保住的关键。
  • 图层号重排：0 底图压暗 / 1 色面 / 2 云纹 / 3 等值线+经纬网 / 4 可信度纱 / 5 方位环 / 6 数值直标 / 7 图钉 / 8 加载遮罩 / 20 提示卡。三处同步：template 注释表（全项目唯一来源）、各层 z-index、.mapwrap.dark 的 filter 名单。
  • 风险兜底：若实测 α 拿不到"看得见又不破 ±2"（其实独立图层已经不破 ±2，剩下的是纯观感问题），退化为"仅图例说明云量、不画纹理"，S1 降级为纯数据准备。

验收：新层存在且有内容；色面不透明像素仍 100% 落在档位色 ±2（既有断言即证明）；云纹像素只出现在色面有像素处、α≤0.2（新增）；缓存 v6 读写正常、旧缓存不炸。

  • 手机上：排行榜默认只显示前 4 条 + "查看全部"展开钮；图例色条与刻度行紧凑化；两处 <details> 摘要文案缩短；工具条组间距收敛。
  • #map 窄屏高度 420 → 460 px（小步，不激进）。
  • mobileprobe 的布局断言要重新量（工具条行高/行数、卡片总高、地图占比），按实测新值更新——这是"一次做全"里明确允许的基线重定，不是放水：判据仍按身份/集合断，不断"元素总数"。
  • 全屏按钮（S5）是手机端的真正答案：卡片里一小条 → 一键全屏。S6 是压缩，S5 是出口，两者互补。

验收：mobileprobe 两档视口 26+2 条全绿（按新实测值）；地图区占模块高度比例实拍对比提升；横向不溢出（约束 46/47 不动）。

  4. 改过探针 ⇒ 跑完 all.py 再跑 docfacts（顺序纪律，约束 49）

六、明确不做的

事项为什么不
换 Leaflet/MapLibre 底图中国区域需测绘资质与审图号，腾讯 SDK 是已验证合规项；对引擎依赖仅"瓦片+投影+事件"，无切换动机
符号点阵地图（弃连续色面）等值线、悬停取值、可信度纱全部建立在连续值场上；丢掉连续性是拿核心能力换观感
按数值分透明度透明度也编码数值 ⇒ "看图反查数值"多一个变量，像素断言全部要重新论证
用 ETOPO1 高程判海M1 轮已实测否掉：10 个已知点判错 2 个，且错的方向最坏（真海判成陆）
磨圆凸包折角第三轮已判定并回退：500 km 尺度下顶点可挪动量仅约 4 px，且与覆盖/可信半径不可兼得
当日拉伸改"直方图均衡"等智能拉伸治的是同一个病，但把"颜色含义"变成一段算法——用户永远说不清某个颜色是多少分。固定刻度 + 云纹 + 等值线已经给了足够结构
全屏态/采样点默认值进偏好持久化图层开关一律不持久化是既有纪律（约束 43）；全屏是临时态，更不该存

七、风险与兜底

风险概率/影响兜底

八、验收清单

  1. 治怪：固定刻度 + 天色色阶 + 有机边缘 + 双降不透明度后，默认取景实拍与 _check/shot-map-desktop.png 对比——色面有结构（≥2 个可辨大区）、底图地名可辨、边缘无折角。
  2. 结构：云纹层在场且不碰色面（mapaudit I 段 offPalette＝0 即证明）；采样点默认开启、57 + 1。
  3. 实用：图例出现"绝对"与读图六件套、不再出现"拉伸"；提示卡首条是距离·方位；全屏进出/Esc/resize 全部端到端通过；手机上地图占比提升且横向不溢出。
  4. 回归：SITE_BASE=sunglow assemble → mkpreview → all.py 全绿（25 项 + 新增断言）；docfacts 0 不一致；产物字节数与文档同步。
  5. 留证：before/after 实拍各一套（桌面 + 窄屏 + 深色底图 + 全屏四态）。
