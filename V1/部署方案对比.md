# 部署方案对比 —— 三条路，以及「B 方案能不能挂在 Cloudflare Pages」

> 结论先行：**B 方案（服务端代转）不需要"自建服务器"这个前提在技术上不成立，但在 Cloudflare 上跑等于白做**。
> Cloudflare Workers 的出站 IP 是全平台共享的，恰好正面撞上 Open-Meteo「按 IP 限流」这条软肋。
> B 方案要有意义，就得拿到**独占出口 IP** —— 那就必须自建。

---

## 0. 先把三个词钉死

| 代号 | 含义 | 请求从哪出 | Open-Meteo 看到谁 |
|---|---|---|---|
| **A** | 纯静态托管，浏览器直连 API（＝现状） | 访客浏览器 | 访客自己 |
| **B** | 服务端代转 + 缓存 | 你的服务端 | 你的服务端 |
| **C** | 自托管 Open-Meteo 服务端 | 你自己的机器 | 没有这一层了 |

**A 的额度是「每位访客各自 10,000/天」，站点本身不消耗配额。**（免费层不发 API key，服务端只能按来源 IP 归属。）
所以 A 在配额上**反而优于 B** —— 它把用量分散到了每个访客头上。

---

## 1. B 方案挂在 Cloudflare Pages 上会怎样

### 技术上完全可行
Cloudflare Pages 自带 **Pages Functions**，`functions/` 目录一放就自动部署，不需要任何服务器运维。
额度与限制（**已核实**，2026-10-10）：

| 项目 | 免费层 |
|---|---|
| 请求数 | **100,000/天**，与 Workers **共享同一个池**（UTC+0 重置） |
| 静态资源请求 | **免费且不限量**，且**不计入**上述 100k（靠自动生成的 `_routes.json` 排除） |
| CPU 时间 | **10 ms / 次调用** |
| subrequests | **50 / 请求** |
| 内存 | 128 MB / isolate |
| 日限额用尽后 | 默认 **Fail open** —— Functions 被旁路，静态资源照常服务 |

对纯代理转发来说这两条限制都**不是问题**：
- **10 ms CPU 够用** —— 等上游网络的时间不计入 CPU，代理只是 `await fetch()` 再返回。
- **50 subrequests 够用** —— 本项目每次取数只有 **2～4 个** upstream HTTP 请求
  （地图那"171 个加权调用"是**计费口径**，实际是 3 个 HTTP 请求、每个带 57 个坐标）。
- **100k/天 够用** —— 每次页面访问只产生个位数 Functions 请求。

条款也不是障碍：Cloudflare 已于 2023 年删掉旧的 §2.8（HTML / non-HTML 那套构造），
内容限制移入 CDN 专属条款，并明确 **Developer Platform 不受此限**，新版条款还写明 CDN 可用于 serving web APIs。

### 但它达不到 B 的目的
B 方案的全部意义是「把额度从访客头上挪到你头上，拿到一份可控的配额」。
在 Cloudflare 上这一步会**失败**：

1. **Workers 的出站 IP 不能指定。** Cloudflare 员工的官方答复是 *"No, this is fully intended"*，
   另有工程师答复 *"Workers will use any IP from the IP pool, and you can't force it to use one"*。
   实测把 Worker 打向 `icanhazip.com`，返回的是同一个 Cloudflare IP。
2. **Open-Meteo 作者本人点名说过这件事**：

   > The limits are 600 calls / min, 5.000 calls / hour and 10.000 calls / day.
   > **Limits are applied on an IP basis. This is not ideal for shared hosting services like cloudflare workers**,
   > but is the easiest and privacy-friendly way to limit access to fair-use.

合起来就是：你代理出去的请求，会和**全球所有在 Cloudflare Workers 上代转 Open-Meteo 的人**，
共用那一份 10,000/天。这个池子几乎不可能还没被打满 —— 缓存未命中的那一次请求就会直接 429。

**换句话说：B 方案在 Cloudflare 上不是"够不够用"的问题，而是"根本用不了"。**

## 2. 三条路的实际取舍

| | A 纯静态 | B 服务端代转 | C 自托管 Open-Meteo |
|---|---|---|---|
| 需要自己的服务器 | 否 | **是**（独占 IP 才有意义，Cloudflare 不行） | **是**（且规格要求高得多） |
| 能挂 Cloudflare Pages | ✅ 最佳场景 | ⚠️ 能跑但失效（见上） | ✅ 静态前端仍可放 |
| 额度风险 | 分散到访客，**最健康** | 集中到你，可控 | **无此问题** |
| 共享 NAT 被陌生人挤掉 | ⚠️ 有 | ✅ 没有 | ✅ 没有 |
| 商业用途限制 | ❌ 受限（免费层仅限非商业） | ❌ 受限（换平台不改变 open-meteo 的条款） | ✅ **可商用**（AGPLv3 开源，数据 CC BY 4.0） |
| 运维成本 | 零 | 低 | 高（要自行同步气象数据，磁盘/带宽开销可观） |
| 额外收益 | — | 能顺带解决腾讯地图代理 | 完全自主 |

### 关于"服务器"这东西
如果将来真要服务端化，那台机器**门槛很低** —— 本项目的服务端只做「代转 + 缓存 + 拼装」，
不做任何计算（光路上的物理模型全在浏览器里跑）。一台最小规格的实例、独占公网 IPv4、能跑
Node 或 Python 即可（供参考的规格门槛：1 核 / 512 MB 起步）。它还能顺带承担第二个角色：

> **腾讯地图代理。** 产物里 `_TMapSecurityConfig.serviceHost` 指向
> `http://127.0.0.1:__WB_HTTP_PORT__/_TMapService/_wbt/__WB_TMAP_SECRET__` —— 这是 WorkBuddy
> 预览环境起本地代理替你转发腾讯地图服务、把 secret 藏在服务端的机制。自己部署时这台 VPS
> 正好可以复用同一角色，`serviceHost` 指向自己的域名 + HTTPS。
>
> **前置条件**：你需要自己去腾讯位置服务申请 key/secret。

### 为什么 C 不划算（现阶段）
C 是唯一能同时摆脱"IP 限流""非商业限制"两条约束的路，但它把「调一个 API」变成了
「运维一套气象数据服务」—— 要自行同步并存储上游气象数据，磁盘与带宽开销远超这个项目的体量。
**除非这个站点真的要对外运营，否则不值得。**

## 3. 建议

**短期（自用 / 小范围分享）：走 A，部署到 Cloudflare Pages。**
- 静态资源请求免费不限量、100 个自定义域名、500 次构建/月 —— 对本项目绰绰有余。
- 额度天然分散在访客头上，站点侧零消耗。
- 需要处置的只有**地图占位符**一件事（两条出路见下）。
- 注意两条与部署无关的既有风险：免费层**仅限非商业**；共享 NAT 出口下会与同 IP 的陌生人共用配额。

**中期（要公开运营）：A 的前端 + 自建 VPS 做 B。**
- 前端仍放 Cloudflare Pages（静态资源免费无限）。
- VPS 承担 `/api/meteo`（代转 + 边缘/服务端缓存）+ `/tmap`（腾讯地图代转）。
- **缓存的键要设计好**：`(纬度取整, 经度取整, 日期, 变量集, 模型)`。
  气象数据 6 小时才更新一轮，TTL 给 1～3 小时完全够 —— 这一层才是 B 的真正价值所在，
  它把「每次访问 171 次调用」压成「每个 (城市, 日期) 组合只取一次」。
- 走到这一步就该同时评估**付费层 Open-Meteo Standard（$29/月，1M 次/月）**，
  它既解除非商业限制，也把限额从"按 IP"变成"按 key"，从根上绕开共享 IP 问题。

**先做一件事验证平台行为**：实际发布一次，确认平台是否会自动替换地图占位符。
这决定了 A 的落地工作量。

## 4. 地图模块能不能保住？—— 能，四条路

**先纠正一个可能被上文误导的判断：地图代理和气象数据代转是两件互不干扰的事。**
上文说"B 方案在 Cloudflare 上失效"，那是**只针对 Open-Meteo**（它按来源 IP 限流，而 Workers 出口 IP 共享）。
**腾讯地图不按来源 IP 限流** —— 它认的是**你自己的 key + 配额（QPS）**。所以：

> **给地图做代理，用 Cloudflare Pages Functions 完全可行，不需要 VPS。**
> 而且走这条路时 `serviceHost` 与站点**同源**，连 CORS 问题都不存在。

### 4.1 先看清楚：产物对地图引擎的依赖其实很薄

`_p6.js` 里用到 TMap 的只有四处：

| 用途 | 调用 |
|---|---|
| 建图 + 投影 | `new TMap.Map` / `new TMap.LatLng` / `map.projectToContainer` |
| 省界图层 | `TMap.MultiPolygon` + `TMap.PolygonStyle` |
| 地图事件 | 拖动 / 缩放 / 键盘 |

而**色面、可信度纱、数值直标、图钉、提示卡、图例全部是自绘的**（独立画布 + DOM），
`TMap.visualization.Heat` 是**刻意不用**的（注释里写明了原因）。地图引擎在这里只承担
「底图 + 经纬度↔屏幕坐标 + 手势」，其余都是这个项目自己的代码。

这一点很重要：它意味着**无论选哪条路，那套自绘图层都不用重写**。

### 4.2 四条路

| | 做法 | 改动量 | 需要什么 | 地图效果 |
|---|---|---|---|---|
| **路 0** | 明文 key（script 上加 `&key=XXX`）+ **Referer 白名单** | **1 行** | 自申请腾讯 key | 完整 |
| **路 1** | 什么都不做，先实测 | **0** | — | **未知**，见下 |
| **路 2** | 官方代理转发（`serviceHost` 指向自己的 Pages Functions） | ~40 行 Function | 自申请腾讯 key | 完整，且 key 不出现在前端 |
| **路 3** | 换地图引擎（Leaflet / MapLibre） | 中等 | 无需 key | ⚠️ **有合规风险，不建议**（见 4.5） |

### 4.3 路 1：先实测，可能根本不用改

`_p6.js:403` 的失败分支把原因分成了三类，但**到底会走到哪一类，只能实测**：

- **库没加载**（`window.TMap` 为空）→ 地图区显示失败文案（`box.innerHTML = mapfail`）
- **库加载了但 `new TMap.Map` 抛错** → 被 `catch` 住，提示"地图初始化失败"
- **库加载了、地图也建起来了**，只有底图/服务类请求 404

注意 `map.qq.com/api/gljs` 这个脚本**本来就不带 key**（官方文档的写法就是如此），
所以脚本本身大概率能正常加载；真正受影响的是 `serviceHost` 那几条服务请求。
**先部署一次看它落在哪一类**，再决定要不要动，成本为零。

### 4.4 路 2：官方方案的确切规格（腾讯地图 glKeyDelegate 文档原文）

这不是逆向，是腾讯位置服务**官方提供**的能力（文档明确写「明文 Key 仅限本地，
公网发布必须改用代理方案」）。代理需要实现**四条路由**：

```nginx
location /_TMapService          → https://pr.map.qq.com/pingd?appid=jsapi_v3      加 &key=
location /_TMapService/checkKey → https://apikey.map.qq.com/mkey/index.php/mkey/check  加 &key=
location /_TMapService/oversea  → https://overseactrl.map.qq.com                   加 &apikey=
location /_TMapService/service  → https://apis.map.qq.com/ws                       加 &key=
```

前端只改两处（**顺序不能反**，配置必须在 API 引入之前）：

```html
<script>
  window._TMapSecurityConfig = { serviceHost: "https://你的站点/_TMapService" };
</script>
<script src="https://map.qq.com/api/gljs?v=1.exp&libraries=visualization"></script>
```

**放到 Cloudflare Pages 上的等价实现**（`functions/_TMapService/[[path]].js`）：

```js
const UP = [
  ["",         "https://pr.map.qq.com/pingd?appid=jsapi_v3", "key"],
  ["checkKey", "https://apikey.map.qq.com/mkey/index.php/mkey/check", "key"],
  ["oversea",  "https://overseactrl.map.qq.com", "apikey"],
  ["service",  "https://apis.map.qq.com/ws", "key"],
];
export async function onRequest({ request, params, env }) {
  const seg = (params.path || [])[0] || "";
  const hit = UP.find(u => u[0] === seg);
  if (!hit) return new Response("not found", { status: 404 });
  const u = new URL(request.url);
  const q = new URLSearchParams(u.search);
  q.set(hit[2], env.TMAP_KEY);          // key 只存在于服务端环境变量
  return fetch(hit[1] + (hit[0] === "service" ? u.pathname.replace(/^.*\/service/, "") : "") + "?" + q,
               { method: request.method, body: request.body });
}
```

要点：
- key 存进 Pages 的环境变量（`TMAP_KEY`），**永不进入前端产物**。
- `serviceHost` 与站点同源 ⇒ **没有 CORS、没有混合内容问题**（前提是站点本身 HTTPS，Pages 默认就是）。
- 产物侧只需把 `tpl/template.html:577` 那行占位符改掉——**注意产物是 `assemble.py` 生成的，不能手改**，
  要改的是模板，或让 assemble 时按环境替换。

**前置条件**：你需要自己去 [lbs.qq.com](https://lbs.qq.com) 申请一个 Web 端 JS API key。

### 4.5 路 3 为什么不建议

换 Leaflet / MapLibre 技术上可行（对引擎的依赖很薄，见 4.1），但：
**在中国区域内展示地图，底图服务需要有测绘资质。** 腾讯地图是合规的，OSM 之类的境外
服务不能拿来展示中国区域。换引擎等于把合规问题一起换进来，为了省一个 key 不值得。

### 4.6 路 0 的风险边界

明文 key 的官方定性是「仅限本地开发/内部预览」。如果只是自用或小范围分享，
**配上 Referer 白名单**（`*.你的域名`）后，即使 key 被扒走，在别人的域名下也用不了 ——
这是官方支持的防护。**公开运营则必须走 路 2**。

### 4.7 结论

> **A 方案不需要舍弃地图模块。**
> 最省事的顺序是：**先部署一次实测（路 1，零成本）→ 若确实不可用，按 路 0 或 路 2 修**。
> 路 2 可以完整地跑在 Cloudflare Pages 上，不需要任何服务器。
> 只有当你**同时**要解决 Open-Meteo 的额度问题（那才需要独占 IP）时，才需要一台 VPS ——
> 而那是另一件事，和地图无关。

### 4.8 路 2 已落地（2026-10-10）

上面 4.4 的骨架已成为仓库里的真实文件：

- `functions/_TMapService/[[path]].js` —— 四条路由 + 路径透传；key 读环境变量 `TMAP_KEY`，
  未配置时返回 **500 并写明原因**（而不是把上游的 4xx 透出去让人去猜）。
- `tpl/template.html` 里的 `serviceHost` 收敛成**一个**占位符 `__TMAP_SERVICE_HOST__`，
  由 `assemble.py` 在构建期注入：设了 `TMAP_SERVICE_HOST` 就用它，没设就回落成
  本地预览的 `__WB_*` 形态（**预览环境行为逐字不变**）。
- 产物里**不允许残留**这个占位符（`assemble.py` 会在写完前检查并失败退出）；
  前端另有 `isMapProxyPlaceholder()` 在运行时兜底识别"未注入"与"纯离线"两种不同原因。
- 部署与本地预览步骤见仓库根目录 `README.md`。
