01项目定位与核心功能

一款可本地运行的朝霞/晚霞（火烧云）定量预报网页产品：输入地点与日期，输出出现概率、六档强度、最佳观赏窗口与预计色彩，并提供全国/城市两级辉光地图与回测验证页。

1.1 产品定位

  • 物理内核 + 薄标定层：预报不是纯统计模型——先算太阳几何、大气光谱消光、云幕受光与光路上游遮挡等物理子评分，再在 logit 空间用岭回归标定为概率（core/model.py 模块 docstring；README「预测逻辑」）。
  • 零密钥主链路：概率计算主链路仅用免费无密钥的 Open-Meteo（ERA5/CAMS 转发）；WeatherAPI、和风天气、官方档案直连均为可选增强（README:44-46；core/config.py:24-28）。
  • 四模式并列而非择一：同一时刻对 Open-Meteo best_match、ECMWF IFS、GFS、ICON 四个场各算一次，并列展示、互不替代；某源无数据时显式显示「数据获取失败」，不静默替换（core/service.py:1-6 模块 docstring；server.py /api/predict 链路）。
  • 两种交付形态：① Python 服务版（本目录主体，server.py + web/ SPA + core/ 后端）；② 单文件网页版 Skyglow-单文件版.html（双击即用，由 tools/make_single.py 合成，算法为 Python 版的逐行 JS 移植）（README:416-514）。

3.2 数据流转：bundle 的内部形状

bundle = {
  "points": [ {id, dist, az, lat, lon,
               "time": ["2026-10-17T00:00", ...],          # 逐时本地时间串
               "sources": { openmeteo|ecmwf|gfs|icon: {
                   cc_low, cc_mid, cc_high,                # 三层云量（各模式一套序列）
                   rh, precip, blh, vis } , ...},
               "aod": [...] } , ... x25 ],                # CAMS，四源共用
  "offset": 28800, "tz": "Asia/Shanghai", "elevation": 5,
  "source": "Open-Meteo forecast" | "ERA5 archive"
}
  • 四源复用什么：一次 URL 带 models=best_match,ecmwf_ifs025,gfs_seamless,icon_seamless，Open-Meteo 按变量后缀返回四套序列；_series() 按 token 取对应序列，因此四源对照不增加配额（core/meteo.py:40-58,195-200；README:163-166）。
  • 上游聚合：以事件时刻太阳方位为中心 ±80° 内按 cos²(Δ/2)、距离按 e^(−d/260) 加权，得 cc_low_up / cc_mid_up / cc_high_up / aod_up；权重和 <0.2 时回退本点值（core/meteo.py:296-341）。
  • 时间插值：线性插值到事件本地时刻，越界取端点、遇 None 取邻点（core/meteo.py:269-282）。

3.6 配额与速率控制（Open-Meteo 按「点数 × 变量 × 天数」加权计费）

  • 令牌桶：滚动 60 s 窗口内地点数 ≤ 430（_BUDGET_MAX），超限睡眠到窗口释放（core/meteo.py:65-66,120-128）。
  • 分块：主链路 25 点一次请求；雷达 77 点；地图 150 点/块（core/glowmap.py:23）。
  • 变量精简：只取模型读取的 7 个变量（三层云量、能见度、湿度、降水、边界层高度），较 11 变量降本约 36%（core/meteo.py:54-59；README:285-287）。
  • 熔断：收到 429 或配额提示即标记转发通道不可用 10 分钟并持久化，后续请求立即失败转直连（实测单次查询 88 s → 2.7 s）（core/meteo.py:68-113；README:333-337）。
  • 重试：非 429 错误指数退避重试 4 次；429 不重试、直接熔断（core/meteo.py:164-192）。
证据本节链路均对照 server.py 路由实现、core/service.py 与 core/meteo.py 函数体逐步核对；bundle 结构照抄 core/meteo.py:243-266 的构造代码。

4.2 启动入口与端口逻辑

  • 唯一入口：python server.py [port]（server.py:1-6,361-402）。
  • 端口优先级：命令行参数 > $PORT > 8770；绑定失败自动尝试 +1～+10，全部占用则退出并提示（server.py:363-381）。
  • 绑定地址：默认 127.0.0.1；设置 $PORT（Render/Railway/Fly 惯例）时自动 0.0.0.0；也可 SKYGLOW_HOST 强制指定。启动横幅始终打印 http://127.0.0.1:<port> 并提示 0.0.0.0 不是可访问地址（server.py:365,387-391；README:36-38）。
  • setup 脚本：建 .venv → pip install -r requirements.txt → import 自检（eccodes/numpy/cryptography）；Windows 下 py → python 探测、venv 创建/安装/验证分阶段报错（setup.bat:1-72 · setup.sh:1-25）。
  • run 脚本：优先 .venv/bin/python（或 .venv\Scripts\python.exe），缺失则回退系统 Python 并提示直连需要 eccodes（run.sh:1-14 · run.bat:1-34）。
  • 可选依赖自检：服务启动时打印缺哪些可选包、各自损失什么、当前解释器的安装命令（server.py:324-357）。
  • 前端入口：GET / → web/index.html；静态资源经 _file() 从 web/ 读取，禁止 .. 逃逸，文本类加 charset=utf-8，Cache-Control: no-cache；HEAD 与 GET 同头（server.py:43-49,302-321）。
  • 单文件版入口：双击 Skyglow-单文件版.html，无需服务器；已缓存查询可离线查看（README:416-426）。

07代码组织与实现层面的关键设计决策

7.1 物理可解释优先，标定层只做「重新加权」

模型先算 7 个有物理意义的子评分（canvas 云幕、canvas_high 高云幕、light 受光、horizon 光路、purity 通透、aod、precip），取 logit 后进入岭回归（α=1.2）得强度潜变量，再用一维 logistic 转概率、按标签累计频率定六档阈值。模块 docstring 明确「回归是标定层而非替代：每一项保留物理含义」（core/model.py:1-14,174-208；tools/calibrate.py:208-229）。等级由潜变量而非概率分档，使「会不会烧」与「烧多旺」两个问题解耦（core/model.py:199-207）。

7.2 25 点上游环带：用实测数据封死了「省额度」的裁剪

上游采样固定为「中心 + 120/250/380 km × 8 方位」共 25 点。README 记录了基于 39 份真实响应、1056 个（事件×源）组合的消融实测：仅中心点最差偏差 42.3pp（场景：太阳方向上游低云 83% 而中心 0%，地平线遮挡因子 0.24→1.00，概率 14%→57%），内环 9 点最差 21.8pp，太阳侧 ±45° 7 点最差 12.7pp——因此环带不做任何裁剪，七日趋势同样用满 25 点（README:289-304；tools/measure_accuracy.py 可离线复现）。

7.3 四源并列与「不静默替换」

四个源在 service._predict_day 中独立评估；无数据的源返回 {"error": "数据获取失败"} 并附具体原因（无官方档案 / 缺 eccodes / 直连关闭 / 历史日期无实时档案），前端芯片标红、tooltip 展示原因（core/service.py:325-338；web/app.js:259-273）。AOD 四源共用并在 UI 注明（免费数据无分模式气溶胶产品）。

7.4 诚实降级语义

  • 直连模式在卡片上固定标注「仅取最近格点，无上游环带」，置信度上限 0.74（转发路径 0.86–0.90），并按四源极差再扣减（core/service.py:14-28,237-239）。
  • ECMWF 官方 0p25 不发布分层云量，直连值由 tcc + 850/500/300 hPa RH 按 Sundqvist 型诊断并以总云量约束缩放，UI 标注「由总云量与湿度廓线诊断，非模式自带分层云量」（core/direct.py:227-303；core/service.py:234-236）。
  • 历史日期（>2 天）不提供直连，明确报错而非编数（core/service.py:302,335-336）。

7.5 校验源边界：只校验、不打分

WeatherAPI 与和风都只有总云量，硬拆三层等于编造模型最依赖的输入，因此二者只做交叉校验与 vis/rh/precip 三项缺测补位（aux_from 记录补位来源），总云量差 ≥35pp 或降水概率 ≥60% 时自动追加风险提示（README:187-214；core/service.py:132-209）。

7.6 显式取数的交互契约，且有自动化断言

前端所有参数变更只调 markDirty()（按钮加亮显示「开始预测 ●」），取数只发生在点击或地名回车；该契约由 tools/verify_interaction.py 以无头浏览器逐步骤断言（打开页面/换城市/改日期/切朝霞均 0 新增请求）（web/app.js:51-59；tools/verify_interaction.py:66-113）。

7.7 缓存 TTL 按「资料还能变多少」制定

昨天及更早永久（再分析定稿）、今天 60 min、明天 3 h、之后 6 h；store.SCHEMA=4 在 payload 结构变化时让旧缓存自然失配；写入用 tmp + os.replace 原子替换，线程锁保护（core/store.py:33-99）。

7.8 工程组织上的其他决策

  • 标准库 HTTP 服务：不引框架，ThreadingHTTPServer 并发；JSON 统一 ensure_ascii=False + no-store；异常统一 500 + traceback 到 stderr（server.py:26-34,94-98）。
  • 中文地名解析的行政区分段：按 _ADMIN 后缀表切段、从最具体一段开始尝试、中文输入优先国内结果、按人口排序；解决了「上海市直查落到伊利诺伊州某村」的问题（core/meteo.py:362-455）。
  • 前后端经自定义事件解耦：app.js 渲染后派发 skyglow:data，analysis.js/maps.js 订阅并各自管理缓存键与请求序号（state.req 竞态防护）（web/app.js:399-419；web/analysis.js:20-77）。
  • 地图按需生成：两张图默认不请求，按钮才触发；切换数据源只重绘；日期/位置变更后按钮回到「生成」；同日期切地点时全国场直接复用、只取新坐标城市场（web/maps.js:499-542；README:142-148）。
  • 移植即验证：单文件版不是重写而是逐行移植，配套三层验证——单元逐值比对（verify_port）、真实数据端到端（verify_real）、渲染冒烟与行为断言（smoke_single / verify_interaction / verify_requests）（README:448-476）。
  • 回测数据治理透明：1109 条标签 100% 进入建表/标定/训练；报告同时交代两条局限——两模型共用同批标签故「交叉比对」非独立验证；部署模型含测试期样本、2023H2 指标偏乐观（README:359-377）。

7.9 已知局限（代码与文档自述）

  • 0.25° 网格平滑掉云缝与云边界，「云洞漏光」无法解析；无云的光学厚度，厚薄卷云被同等对待。
  • 气溶胶垂直廓线未知，等效消光高度有 ±1 km 量级不确定性。
  • 标签来自上海单点人工观测；跨气候区使用需重新标定阈值。
  • 历史日期用 ERA5 再分析（事后最优估计）精度高于当时的业务预报；15 天以外不预报。
  • 强度分级是弱项：六档中 83% 为「基本不烧」，可用于区分强度的样本仅 188 条。
